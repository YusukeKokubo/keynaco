# POC260529: Zenzai personalizationMode（n-gram 補間）の効果検証

status: tested（2026-05-29 計測完了）/ 判定: 機構は有効だが**データ量がボトルネック**。経過観察（データ蓄積）待ち
関連: [IDEA260529](../ideas/IDEA260529.md) #1 / 先行例 [POC260524](POC260524.md)（leftSideContext の効果実証）

## 仮説

zenz-v3 の `personalizationMode`（base/personal n-gram LM の KN 補間バイアス）を有効化すると、
ユーザーの過去の確定テキストに頻出する語が同音異義語の選択で優先され、`leftSideContext`
（直近文脈）だけでは拾えない「その人固有の語彙・言い回しへの恒常的適応」が得られる。

## 機構（コード読解で確定済み）

AzooKey 0.11.x（`Core/.build/checkouts/AzooKeyKanaKanjiConverter`）の実装を読んだ結果：

- API: `ZenzaiMode.on(weight:inferenceLimit:requestRichCandidates:personalizationMode:versionDependentMode:)`
  - `PersonalizationMode(baseNgramLanguageModel: String, personalNgramLanguageModel: String, n: Int = 5, d: Double = 0.75, alpha: Float = 0.5)`
  - 引数は**ファイルパスのパターン文字列**（`<pattern>_c_abc.marisa` 等5ファイルを読む）。
- バイアス適用箇所: `ZenzContext.swift:492-510`。LLM デコードの各トークンで
  ```
  logp' = logp + alpha · (log P_personal(token|prefix) − log P_base(token|prefix))
  ```
  - personal が base より高評価するトークンを `alpha` の強さで押し上げる**相対ブースト**。
  - `prefix.isEmpty`（候補先頭トークン）では両者0 → バイアスなし。2トークン目以降で効く。
  - base か personal の確率が実質0の候補はスキップ（+1e-7 フロアあり）。
- モデル生成: `EfficientNGram` ターゲットの `trainNGram(lines:n:baseFilePattern:outputDir:)`。
  内蔵 `ZenzTokenizer()` を使うので学習に外部 HF tokenizer DL は不要。`.marisa`（SwiftyMarisa）5本を出力。

## リファレンス実装（azooKey-Desktop）

- base モデル: `azooKeyMac/Resources/base_n5_lm`（n=5, marisa, Git LFS 同梱）。
- personal モデル: 別パッケージ **Tuner**（github.com/azooKey/Tuner）がフロントアプリのテキストを
  バックグラウンド取得・フィルタ・idle 検出して `lm_*.marisa` を逐次生成。

## feasibility gate（実装前に潰すべき2点）

1. **base モデルの入手**: パッケージ非同梱。azooKey-Desktop の `base_n5_lm`（LFS）を取得して
   実験用リソースとして借りる。ライセンス確認は本採用前に必須（公開前 mozc 帰属と同様の論点）。
2. **personal モデルの生成手段**: `trainNGram` のある `EfficientNGram` は AzooKey パッケージの
   **非公開ターゲット**（`products:` に SwiftUtils / KanaKanjiConverterModule(+WithDefaultDictionary)
   しかない）。よって `KeynacoCore` から `import EfficientNGram` でアプリ内学習はできない。
   - 推論側は `PersonalizationMode` が public でパスを渡すだけなので問題なし。
   - → **効果測定 POC ではモデル生成をオフラインで行い、推論のみ keynaco で測る**。
     本採用するなら (a) AzooKey をフォークして EfficientNGram を product 公開、
     (b) Tuner をパッケージ依存に追加、(c) 学習だけ別 CLI 実行、のいずれかが必要。

## 実験計画（段階）

### Phase 0: モデル準備（オフライン）
- azooKey-Desktop を clone、LFS pull で `base_n5_lm` を取得。
- keynaco の `history.db` から確定 output テキストを行単位で抽出 → `trainNGram(lines:n:5:...)` で
  personal モデル `keynaco_personal_n5` を生成（AzooKey をローカル clone し EfficientNGram を
  ローカルターゲットとして叩く小さな executable で実行）。

### Phase 1: 効果測定（/keynaco-ime-sandbox、POC260524 方式）
- `ZenzaiSettings.makeConverter()` を一時改造し、両モデルパスを `PersonalizationMode` で渡す。
- 同音異義語・固有名詞の読みを複数用意し、`alpha ∈ {0, 0.3, 0.5, 0.8}` で候補順を A/B 比較。
  - 比較軸: personalization なし（現状）vs あり。leftSideContext は両方 OFF にして純粋効果を見る、
    その後 ON にして leftSideContext と二重バイアスの干渉を見る。
- 計測: top 候補 / fixedEnd / Zenzai プロモート行の変化、応答時間。

### Phase 2: 判断
- 効果が体感レベルで出る & 既存 history スコアと喧嘩しない → 本採用設計（gate #2 の (a)/(b)/(c)）へ。
- leftSideContext で既に賄えている（POC260524 の topic と同じ結末）→ rejected.md 行き。

## 探りたいこと
1. personal だけ強くすると common word も無差別ブーストされて過学習しないか（base の役割確認）。
2. keynaco の history は「確定 output」の羅列で文ではない。n-gram 学習に十分な連接情報があるか。
3. 既存の history スコア式ランキング（buildCandidateList §4）との役割分担・二重計上の懸念。
4. レイテンシ: 毎トークン marisa 2本 lookup のコスト（autoShow パスに載せられるか）。

## 検証結果（2026-05-29）

### 実施した内容（フルセットアップ→計測まで）

1. **学習ツール**: `/tmp/azk-train` に EfficientNGram ソース＋tokenizer を切り出した最小 SwiftPM
   package を作り（`#if canImport(SwiftyMarisa) && Zenzai` ガードのため `.define("Zenzai")` 必須）、
   `trainNGram(lines:n:baseFilePattern:outputDir:)` を叩く executable を用意。
2. **base モデル**: azooKey-Desktop が submodule で参照する HuggingFace `Miwa-Keita/base_n5_lm`
   を clone（4ファイル・計43MB・prefix `lm`、n=5）。リファレンス結線は
   `azooKey-Desktop/Core/.../SegmentsManager.swift:89-113`（base=`Resources/lm`, personal=`p13n_v1/lm`）。
3. **personal モデル**: keynaco `history.db` の `daily_log.committed_text`（156行・**わずか2470文字＝2日分**）
   から n=5 で学習。`history` テーブル（6610行）は単語単位で連接情報が薄いため不採用。
4. **計測ハーネス**: `/tmp/azk-measure`（公開 product `KanaKanjiConverterModuleWithDefaultDictionary`
   ＋Zenzai trait、実 gguf = keynaco の zenz-v3.1-small）。同じ読みを α∈{0,0.5,1.0,2.0} で変換比較。

### 結果

| 読み | α=0（現状） | α=0.5〜 | 評価 |
|------|------------|---------|------|
| めいし | 名刺 / 名詞 / … | **名詞** / 名刺 / … | ✅ 意図どおり（コーパスに「名詞/固有名詞」頻出）。**左文脈なしで効いた** |
| どうし | どうし / 同士 / 動詞 | **どう思 / どう死** / … | ❌ 「どう思う」を過剰ブーストし壊れた断片 |
| きょうか | 強化 / … | α≥1.0 で **強下**（非語） | ❌ 過学習 |
| かんかく | 感覚 / 間隔 / … | α=2.0 で **感書ク/感描く**（崩壊） | ❌ 高αで破綻 |
| こうほ/へんかん/さじぇすと/どきゅめんと | — | 変化なし | ー |

### 判明したこと（探りたいことへの回答）

1. **過学習は実在**。base があってもスパースな personal（2470字）では高αで非語を生成する。
2. **history は文として不十分**。`daily_log` の文ストリームを使ってもデータ量が致命的に少ない
   （azooKey の Tuner は数週間蓄積する前提）。これが今回の**律速**。
3. **leftSideContext とは直交（重要）**。`めいし`（左文脈なし）で効いた＝topic（POC260524）と違い
   leftSideContext の冗長ではない。ユーザー語彙への恒常適応という別軸の価値がある。
4. レイテンシは未計測（機構の有効性確認を優先したため）。

### 結論・方針

- **棄却ではない**。機構は正しく動き、データさえ十分なら「名詞」例のような恒常適応の価値がある。
  leftSideContext と冗長でない点が topic と決定的に違う。
- ただし**現状はデータ量が足りず、無理に効かせる（高α）と破綻する**。本採用には
  (a) 数週間〜のテキスト蓄積（Tuner 相当のバックグラウンド学習基盤）と
  (b) gate #2 の EfficientNGram 取り込み（フォーク/Tuner 依存/別CLI）が前提。
- **次アクション**: `daily_log` の蓄積を継続し（既に記録基盤はある）、データが数万字規模に育った時点で
  α=0.3〜0.5 の安全域で再計測する。本 POC を status=tested のまま「データ待ち」で保持する
  （未実装なので observation.md=実装済み機能リストには載せない）。
- 再現資材: `/tmp/azk-train`（学習）・`/tmp/azk-measure`（計測）・`/tmp/base_n5_lm`（base モデル）。
  これらは tmp なので、再開時は本ドキュメントの手順から再構築する。

### 本採用時の論点（先送り）
- base モデル `Miwa-Keita/base_n5_lm` のライセンス確認（公開前の mozc 帰属と同種の論点）。
- personal 学習を**いつ・どのスレッドで**回すか（確定のたび？ idle 時バッチ？）。llama と同じく
  marisa I/O を `LockedConverter` の不変条件と衝突させないこと。

### Tuner 追加の検討（2026-05-29・結論: 今は追加しない）

personal モデル生成・データ蓄積の手段として azooKey の **Tuner**（github.com/azooKey/Tuner, MIT）
を keynaco に足すか検討した。

**Tuner の正体**: SwiftPM ライブラリではなく**独立した macOS メニューバーアプリ**（`.xcodeproj`）。
2層に分かれる:
1. **取得層**: アクセシビリティ API で**全アプリの画面テキストを常時スクレイピング**。
   `NSAccessibilityUsageDescription` 必須、`app-sandbox: false`。
2. **学習パイプライン層**: JSONL 蓄積 → MinHash＋前方一致で重複除去（`MinHashUtils`,
   `TextModel+Purification`）→ EfficientNGram で n-gram 逐次学習（`TextModel+NGram`）。
   App Group `group.dev.ensan.inputmethod.azooKeyMac` 経由で IME にモデルを渡す。

**そのまま追加は却下**。理由:
- keynaco は `app-sandbox: true`／concept.md「ローカル完結」「学習データはローカル SQLite に閉じる」。
  Tuner の取得層は**サンドボックス解除＋Accessibility 権限＋閲覧内容の全収集**を要求し、
  「入力を学習」から「画面で見た全テキストを収集」へ信頼契約が質的に変わる。ポジショニングと衝突。
- azooKey が AX スクレイピングをする理由は「入力だけだとデータが貯まるのが遅いから」＝本 POC の
  データ量律速の解決策だが、keynaco にとっては**最も避けるべき取り方**。
- keynaco は IME なので取得層は**そもそも不要**。`daily_log`（打鍵＋app_bundle_id）が
  プライバシーを守ったまま育つドメインコーパスになる。量の問題は keynaco が新しいだけで時間が解決。

**将来 personalization を本採用するなら**: Tuner 一式ではなく、(1) `daily_log` からの増分学習
（本 POC の trainNGram ハーネスの延長）＋ (2) **dedup ロジックだけ MIT 流用**（Tuner の MinHash／
前方一致は実装の質が高い）を在 keynaco の増分トレーナーに組み込むのが、ポジショニング整合の唯一の筋。
取得層は捨てる。

## 改善 A: Successor 高信頼候補の即時表示

### 現状の問題

`suggestSuccessors()` は N-gram 候補が存在する場合、必ず `pendingSuccessorCandidates` に保存して `.dismiss`（ウィンドウ閉じる）を返す。ユーザーが 1 打目を入力して初めてウィンドウが開く。

```
東京 確定 → （候補ウィンドウ閉じる） → n → 「について」表示 → Space
          ↑ ここで既にほぼ確定している場合でも1打必要
```

count が高い（何十回も同じペアを使っている）場合でも遅延は起きる。

### 目標

`fetchBigramTop(prev:)` の先頭候補の raw count が閾値以上のとき、確定直後に即時表示する。1打目入力を待たず Space 1打で確定できるようになる。

```
東京 確定 → 「について」即時表示 → Space  （1打削減）
```

使えば使うほど閾値を超えるペアが増え、打鍵数が自然に減っていく。

### 設計

**`DatabaseManager` に `fetchBigramTopCount` を追加**：

```swift
/// prev に続く bi-gram の先頭候補の count を返す。直近 90 日以内に使ったエントリのみ対象。
/// 即時表示の閾値判定用。
func fetchBigramTopCount(prev: String) -> Int {
    let cutoff = nowEpoch() - 90 * 86400
    var stmt: OpaquePointer?
    let sql = "SELECT MAX(count) FROM bigram WHERE prev = ? AND used_at > ?"
    defer { sqlite3_finalize(stmt) }
    guard sqlite3_prepare_v2(db, sql, -1, &stmt, nil) == SQLITE_OK else { return 0 }
    bindText(stmt, 1, prev)
    sqlite3_bind_int64(stmt, 2, cutoff)
    guard sqlite3_step(stmt) == SQLITE_ROW else { return 0 }
    return Int(sqlite3_column_int(stmt, 0))
}
```

> **注**: `AND used_at > (now - 90日)` を付けることで「直近90日以内に使ったことがある & count ≥ 閾値」という条件にする。昔高頻度だったが最近使っていないペアの誤即時表示を防ぐ。

**`InputHandler` に閾値定数を追加**（`InputHandler.swift`）：

```swift
static let successorImmediateThreshold = 5  // 直近90日以内にこの回数以上使ったペアは即時表示
```

**`suggestSuccessors()` の分岐を変更**（`InputHandler+SuccessorMode.swift`）：

```swift
if predictTop.isEmpty {
    // 格助詞 fallback のみ → 従来通りすぐ表示
    pendingSuccessorCandidates = []
    return .show(candidates: candidates, historyEnd: 0, initialRow: 0)
} else {
    // ★ 高信頼チェック
    let topCount = db.fetchBigramTopCount(prev: last)
    if topCount >= InputHandler.successorImmediateThreshold {
        // 高信頼 → 即時表示
        pendingSuccessorCandidates = []
        return .show(candidates: candidates, historyEnd: 0, initialRow: 0)
    } else {
        // 通常 → 1打目まで待つ
        pendingSuccessorCandidates = candidates
        return .dismiss
    }
}
```

### 対象ファイル

| ファイル | 変更内容 |
|---------|---------|
| `Sources/DatabaseManager.swift` | `fetchBigramTopCount(prev:)` を追加 |
| `Sources/InputHandler.swift` | `successorImmediateThreshold` 定数を追加 |
| `Sources/InputHandler+SuccessorMode.swift` | `suggestSuccessors()` に高信頼分岐を追加 |

### テスト

- bigram `(東京, について, について)` の count を `successorImmediateThreshold` 未満に設定 → 確定後 `.dismiss`（遅延表示）
- count を閾値以上に設定 → 確定後 `.show`（即時表示）
- trigram が閾値以上でも同様に即時表示されること
- 格助詞 fallback のみのケースは閾値に関わらず即時表示のまま（変更なし）

### リスク

- 閾値 5 は経験則。ノイズが多ければ 10 に上げる。実運用後に調整する
- trigram の count は `fetchBigramTopCount` では取れない。trigram 高信頼は bigram の count 間接評価で代替（trigram が存在するということは bigram も学習済みのはず）

## 改善 B: `pendingRomaji` フェーズの先読み予測

### 現状の問題

コードを調査した結果、**提案4の当初案（1文字prefix記録）はすでに LIKE prefix matching で実質的にカバーされている**ことがわかった：

- `fetchBigram(prev:reading:)` は `input LIKE reading || '%'` なので、`reading = "に"` のとき `input = "について"` の行が自動でマッチする
- `fetchHistoryPrefix` も同様に LIKE でマッチ

ただし**本物のギャップ**がある：ローマ字入力の途中段階（`pendingRomaji`）では `composedHiragana` がまだ空のため、`buildCandidateList` が呼ばれない。

```swift
// InputHandler+Candidates.swift:229
let hasBigramContext = lastCommittedOutput != nil && !state.composedHiragana.isEmpty
//                                                    ↑ composedHiragana が空なら false
```

具体的に起きていること：

```
東京 確定
→ n を入力: pendingRomaji="n", composedHiragana=""
  → hasBigramContext = false → buildCandidateList 呼ばれない → 候補非表示
→ i を入力: pendingRomaji="", composedHiragana="に"
  → hasBigramContext = true → buildCandidateList → 「について」表示
```

`n` 1打の段階でもう予測が出れば `i` の 1打を省ける。

### 目標

`pendingRomaji` が 1 文字かつ bigram コンテキストがあるとき、`romajiToInitialKana` でありうるかな行を取得してbigramを先読みし候補表示する。

```
東京 確定
→ n を入力: 「な行/に/ぬ/ね/の」候補を先読み → 「については」「について」が表示
→ そのまま Space → 先頭候補確定  （i を打たずに済む）
```

### 設計

`composedHiragana` が空で `pendingRomaji` が1文字（かつ `n` 以外）のとき、`buildCandidateList` の代わりに `buildPendingCandidateList(pendingChar:)` を呼ぶ。

> **`n` を除外する理由**: `n` は `ん` になりうる（`na/ni/...` で行確定、`nn` で `ん`）。先読みの方向が曖昧なので対象外にする。

**確定フローの設計方針（先読み確定は Successor モードに吸収）**

先読み中に Enter/Space で候補確定すると、`composedHiragana = ""` / `pendingRomaji = "k"` の状態で `doConfirmSelection` が呼ばれ、`state.finalizedText = forceFinalize("k") = "か"` が reading として `recordPrefixes` / `recordBigram` に渡ってしまう。これは誤記録になる。

対処として **先読み候補が存在した場合に Successor モードへ移行**する（選択肢 c）。`buildPendingCandidateList` が候補を返したら `state.pendingRomaji` を破棄し `isSuccessorMode = true` を立てる。以降の Space/Enter は `handleSuccessorMode` が処理し `confirmSuccessor` を呼ぶ。`confirmSuccessor` は `state.finalizedText` を使わず候補テキストをそのまま記録するため、誤読み問題が起きない。

**`InputHandler+Candidates.swift` に新メソッド追加**：

```swift
/// pendingRomaji が 1 文字の段階で bigram を先読みして候補表示する。
/// 候補が存在すれば pendingRomaji を破棄し isSuccessorMode = true を立てて返す。
/// composedHiragana が空のとき限定で呼ぶ。
mutating func buildPendingCandidateList(pendingChar: String, client: TextInputClient) -> CandidateAction {
    guard let kanas = InputHandler.romajiToInitialKana[pendingChar],
          let prev = lastCommittedOutput else { return .dismiss }
    var candidates: [String] = []
    for kana in kanas {
        let fromTrigram: [String] = prev2Output.map {
            db.fetchTrigram(prev2: $0, prev1: prev, reading: kana)
        } ?? []
        let fromBigram = db.fetchBigram(prev: prev, reading: kana)
        let fromSkip = mostRecentContentWord().map {
            db.fetchSkipBigram(prev: $0, reading: kana)
        } ?? []
        for s in fromTrigram where !candidates.contains(s) { candidates.append(s) }
        for s in fromBigram where !candidates.contains(s) { candidates.append(s) }
        for s in fromSkip where !candidates.contains(s) { candidates.append(s) }
    }
    guard !candidates.isEmpty else { return .dismiss }
    // 候補あり → pendingRomaji を破棄して Successor モードに移行
    state.pendingRomaji = ""
    isSuccessorMode = true
    successorFirstChar = nil
    pendingSuccessorCandidates = []
    // Successor モード中は setMarkedText に実テキストを渡す（Electron 対策）
    client.setMarkedText(candidates[0], selectionRange: NSRange(location: candidates[0].count, length: 0))
    let fixedCandidates = kanas  // ひらがな固定候補
    let allCandidates = fixedCandidates + candidates.filter { !fixedCandidates.contains($0) }
    return .show(candidates: allCandidates, historyEnd: 0, initialRow: fixedCandidates.count)
}
```

**`handleNormalInput` の呼び出し側を変更**（`InputHandler+Candidates.swift`）：

```swift
let needsRefresh = state.addRomaji(base)
let hasBigramContext = lastCommittedOutput != nil && !state.composedHiragana.isEmpty
// ★ 追加: pendingRomaji 先読み（composedHiragana がまだ空で pending が1文字, n 以外）
let pending = state.pendingRomaji
let hasPendingPreview = lastCommittedOutput != nil
    && state.composedHiragana.isEmpty
    && pending.count == 1
    && pending != "n"
    && InputHandler.romajiToInitialKana[pending] != nil

let candidateAction: CandidateAction
if needsRefresh || hasBigramContext {
    candidateAction = buildCandidateList(autoShow: true)
} else if hasPendingPreview {
    candidateAction = buildPendingCandidateList(pendingChar: pending, client: client)
} else {
    candidateAction = .dismiss
}
// ★ 先読み → Successor 移行済みの場合は applyMarkedText をスキップ。
// buildPendingCandidateList が setMarkedText(candidates[0]) を呼んだ後なので、
// ここで applyMarkedText("") を走らせると Electron 対策が無効化される。
if !isSuccessorMode {
    applyMarkedText(candidateText: nil, client: client)
}
```

| ファイル | 変更内容 |

### テスト

- `東京` 確定後 `k` を入力 → bigram `(東京, か行*, ...)` に学習済みデータがあれば候補表示 + `isSuccessorMode = true` になっている
- 候補表示後 Space → `handleSuccessorMode:space` → `confirmSuccessor` → `bigram(東京, "について", "について")` が記録される（"か" ではない）
- `東京` 確定後 `n` を入力 → 先読みなし（候補非表示のまま）。`ni` で `に` になった段階で通常の bigram 表示
- bigram が空のとき → `buildPendingCandidateList` が `.dismiss` → 先読みモードに入らず、`pendingRomaji = "k"` のまま通常組成が続く
- 先読み後に Escape → `isSuccessorMode` をクリアして待機へ（既存 Successor モードの Escape 処理が流用できる）
- `pendingRomaji` が 2 文字になった段階（例: `sh`）は対象外（`pending.count == 1` ガード）
- **Electron 対策の検証**: 先読み → Successor 移行後、`MockTextClient` の最後の `setMarkedText` 引数が `candidates[0]`（空でない）であること。`applyMarkedText` による上書きがないことを確認する

### リスク

- **ノイズ増加**: `k` 1打で `か行` 全体の bigram が出る。使い始めは候補が多くなりうる。recency スコアが育てば自然に絞れるはず
- **先読みモードと通常 Successor の競合**: `isSuccessorMode` を先読みでも立てるため、既存の Successor モードのテストに影響しないか確認が必要
- **先読みキャンセル後の pendingRomaji**: `buildPendingCandidateList` が `.dismiss` を返したとき（候補ゼロ）は `pendingRomaji` をそのまま残す。通常の組成処理が続く

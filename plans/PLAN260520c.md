# noun_bigram テーブル導入計画

## 目的

現在の `bigram` テーブルは格助詞パターン（`東京→は`、`計画→を`）や述語パターン（`雨→です`）が上位を占め、予測価値が低い。名詞→名詞のペアのみを記録する `noun_bigram` テーブルを導入し、Successor モードと通常変換の精度を高める。

## 現状の問題

実 DB 調査（2026-05-20）より：
- ユーザー学習 bigram 2924 行のうち上位は助詞パターンが多数
- `noun_bigram` があれば `skip_bigram`（734 行）も目的が重複するため廃止できる
- `bigram` の `is_preset=1` 行（1054 行）は preset_bigram.csv 由来で独立しているため別途検討

## 設計方針

### noun_bigram の prev の定義

> **直前に確定した名詞まで遡る**（助詞・動詞が間に入っていてもよい）

例：`東京 → は → 雨` のとき、雨の noun_bigram は `prev="東京"`。

これは現在の skip_bigram の役割も兼ねるため、skip_bigram を廃止できる。

### pos 分類との非同期問題

pos 分類は LLM で非同期に行われる（`LLMPOSClassifier`）。確定時点では pos が不明。

**解決策：`prevNoun` を確定時点でキャプチャする**

```
commitText 時:
  prevNoun = InputController.lastConfirmedNounOutput  ← その時点の値をキャプチャ

LLM 分類完了後:
  if pos == "noun":
    recordNounBigram(prev: prevNoun, input: reading, output: output)
    InputController.lastConfirmedNounOutput = output  ← 次の語のために更新
```

`prevNoun` はクロージャが生成された瞬間（= 確定時）の値を捕捉するため、LLM 完了順序が前後しても正しい順序を維持できる。

### reading の取得

`schedulePOSClassification` 呼び出し時点では `handler.state.composingText` が空になっているため、reading を別途渡す必要がある。

→ `InputHandler.lastCommittedReading: String?` を追加し、`commitText` 内で確定直前にセット。

## 実装ステップ

### Step 1: DB テーブル追加（`DatabaseManager.swift`）

```swift
CREATE TABLE IF NOT EXISTS noun_bigram (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    prev    TEXT    NOT NULL,
    input   TEXT    NOT NULL,
    output  TEXT    NOT NULL,
    count   INTEGER NOT NULL DEFAULT 1,
    used_at INTEGER NOT NULL,
    UNIQUE(prev, input, output)
);
CREATE INDEX IF NOT EXISTS idx_noun_bigram ON noun_bigram(prev, input);
```

### Step 2: DB メソッド追加（`DatabaseManager+Ngram.swift`）

- `recordNounBigram(prev: String, input: String, output: String)`
  - `ON CONFLICT ... DO UPDATE SET count = count + 1, used_at = ...`
  - `prev` が nil のときは何もしない
- `fetchNounBigram(prev: String, reading: String) -> [String]`
  - 読み前方一致、recency スコア順
- `fetchNounBigramTop(prev: String, limit: Int) -> [String]`
  - Successor モード用（reading なし）

### Step 3: InputHandler に lastCommittedReading を追加（`InputHandler.swift`）

```swift
public var lastCommittedReading: String? = nil
```

`commitText` 内で `state.composedHiragana` をクリア前にセット。

### Step 4: InputController に lastConfirmedNounOutput を追加（`InputController.swift`）

```swift
var lastConfirmedNounOutput: String? = nil
```

### Step 5: schedulePOSClassification の修正（`InputController+LLM.swift`）

```swift
func schedulePOSClassification(output: String, reading: String) {
    let db = handler.db
    let prevNoun = lastConfirmedNounOutput  // 確定時点でキャプチャ
    Self.posClassifier.classify(output: output) { [weak self] classifiedOutput, pos in
        db.updatePOS(output: classifiedOutput, pos: pos)
        if pos == "noun" {
            if let prev = prevNoun {
                db.recordNounBigram(prev: prev, input: reading, output: classifiedOutput)
            }
            self?.lastConfirmedNounOutput = classifiedOutput
        }
    }
}
```

### Step 6: 呼び出し側の修正（`InputController.swift`）

```swift
// before:
schedulePOSClassification(output: adapter.lastInsertedText)

// after:
schedulePOSClassification(
    output: adapter.lastInsertedText,
    reading: handler.lastCommittedReading ?? ""
)
```

### Step 7: Successor モードで noun_bigram を優先（`InputController+LLM.swift`, `InputHandler+SuccessorMode.swift`）

`applySuccessorLLMScheduling` の examples 生成で `fetchNounBigramTop` を使う。
`fetchBigramTop` の前に `fetchNounBigramTop` の結果を先頭に配置。

### Step 8: 通常変換候補への組み込み（`InputHandler+Candidates.swift`）

`bigramRaw` と同じタイミングで `nounBigramRaw` を取得し、先頭に挿入。

### Step 9: skip_bigram の廃止

- `recordSkipBigram` の呼び出しを削除
- `fetchSkipBigram` / `fetchSkipBigramTop` の呼び出しを削除
- テーブルは DROP せず残す（既存 DB との互換性、後で migration）

### Step 10: bigram 記録の段階的廃止

noun_bigram が十分に機能することを確認してから：
- `recordNgrams` / `recordBigram` の呼び出しを無効化
- `fetchBigram` / `fetchBigramTop` の呼び出しを noun_bigram に差し替え
- preset_bigram（is_preset=1）の扱いは別途検討（格助詞→名詞パターンとして有用）

## 注意事項

- `LLMPOSClassifier` は Apple Intelligence が有効でない環境では何もしない。その場合 `lastConfirmedNounOutput` は更新されないため noun_bigram も蓄積されないが、機能は継続する（bigram が残っている間はフォールバック）
- セグメントモード（複数文節）の確定では reading が文節ごとに分かれる。Step 5 は単文節確定のみ対象とし、セグメントモードは別途対応
- `lastConfirmedNounOutput` はセッションをまたいでリセットしない（`committedHistory` が消えても noun の文脈は維持）

# POC260529c: Zenzai inferenceLimit チューニングの効果検証

status: tested（2026-05-29）/ 判定: inferenceLimit=**非レバー（5 で最適）**／モデルサイズ=**small がベスト**、
v3.2-small ドロップインは**低リスクな微positive（回帰0・微改善・約8%高速）だが任意**・本命の右文脈は AzooKey 更新前提
関連: [IDEA260529](../ideas/IDEA260529.md) #4 / 姉妹 POC [POC260529](POC260529.md)・[POC260529b](POC260529b.md)

## 仮説

`inferenceLimit`（zenz の制約絞り込みループ最大反復数、keynaco デフォルト 5・範囲 1-50）を
上げると変換品質が上がるのでは。品質↔レイテンシのフロンティアがどこか未測定だった。

## 機構（コード読解）

`zenzai.swift:99-160` の reviewLoop。LLM が候補を評価→却下なら prefix constraint を絞って再ドラフト、
を繰り返す。**inferenceLimit はこのループの上限（cap）**で、0 になると現在の best を打ち切り返却する。
= 「目標値」ではなく「上限」。LLM が最初のドラフトを承認すれば 1 反復で抜け、cap には達しない。

## 検証方法（キャッシュ回避）

`/tmp/azk-measure` の `inferlimit` ターゲット。実 gguf（zenz-v3.1-small）で実測。
- **ZenzaiCache 短絡に注意**: 同一 converter で同一入力を繰り返すとキャッシュヒットして実推論を測れない
  （初回計測で limit=1 が 5-8ms 一定・top 不変という誤結果が出た）。
  → 計測ごとに **fresh converter** を作り、モデルロードは別入力（"てすと"）で先に払い、
    対象読みは未キャッシュの1回だけ計測する方式に修正して再計測。

## 結果（2026-05-29）

簡単な入力（短い同音異義＋文脈・通常の文）は limit に関わらず top 不変・~12-35ms。
**難・同音異義の長文で cap が効く**ことを確認:

| 入力 | limit=1 | limit=2〜3 | 収束点 | レイテンシ推移 |
|------|---------|-----------|--------|--------------|
| きしゃのきしゃがきしゃできしゃした | 記者で記者**下**（誤尾） | 記者**した** | 2 | 32→32→37ms |
| このはしわたるべからず | 此橋渡る | 此はしわたる | 3 | 28→42→52→67(5)ms |
| すもももももももものうち | すもも…**桃のうち**（誤） | 全ひらがな（正） | 2 | 34→29ms |
| わたしはきょうかいしゃにいく | 私は今日会社に行く | 同じ | 1 | ~25ms |
| かれがくるまではしずかだった | 彼が来るまでは静かだった | 同じ | 1 | ~42ms |

## 判明したこと

1. **inferenceLimit は確かに効く**: 難ケースで limit=1 は早期打ち切り → 誤変換（記者下・桃のうち）。
2. **収束は全ケース limit≤3**。limit=5/10/15/30 にしても top は1件も改善しない（測定範囲で）。
3. **レイテンシは実反復数に比例**。cap が高くても LLM が承認すれば反復は止まるので、
   高 cap は「難ケースで反復が伸びうる」だけ。簡単な入力の latency は cap 非依存。

## 結論・判定

- **デフォルト inferenceLimit=5 は良い設定。変更不要＝非レバー。**
  - 5 は収束点（≤3）を余裕で上回る → 難ケースも取りこぼさない。
  - 5 超は測定上ゼロ改善・レイテンシのみ増の純損。
  - 3 未満は曖昧入力で品質劣化リスク（記者下・桃のうち）。
- **モデルサイズ（2026-05-29 調査・実測済み）** → 下記「モデルサイズ / v3.2 ドロップイン」参照。
  結論: サイズ軸では small がベスト（v3 に medium/large は存在しない）。v3.2-small ドロップインは
  回帰0・微改善・微高速だが mild。右文脈の本命機能は AzooKey 更新が前提。

## モデルサイズ / v3.2-small ドロップイン（2026-05-29）

### ラインナップ調査（Miwa-Keita / HuggingFace）

| 世代 | サイズ | 条件付き変換 |
|------|--------|------------|
| v3.1-xsmall | 22.5M | あり |
| **v3.1-small（keynaco 現在）** | 90.5M | あり（leftSideContext） |
| v3.2-small | 95.1M | あり＋**右文脈 ``**（azooKey-Desktop 現行） |
| v2.5-medium | より大 | **なし**（v2.5 世代） |

- **v3 世代に medium/large は存在しない** ＝ small が事実上の上限。より大きい v2.5-medium は
  v3 の条件付き変換（leftSideContext = killer feature, POC260524）を失うので不可。
  xsmall 縮小は品質低下のみで動機薄（現レイテンシ ~12-67ms は許容内）。→ **サイズ軸では small がベスト。**
- v3.2 の右文脈（``）は **AzooKey 0.11.2 の API では扱えない**
  （`ZenzaiVersionDependentMode` は `.v3` のみ・右文脈フィールドなし）。活かすには AzooKey 更新＋配線が前提。

### v3.2-small ドロップイン実測（右文脈なし・新重みのみ・inferenceLimit=5）

`/tmp/azk-measure` `modelcmp` ターゲットで v3.1-small vs v3.2-small を比較（fresh converter でキャッシュ回避）。

- **計28ケース（難・同音異義8 + 日常/ビジネス語20）**: **回帰0件**。
- 改善2件: `このはしわたるべからず` v3.1=「此はしわたるべからず」(63ms・崩壊) → v3.2=「**この橋渡るべからず**」(24.6ms)／
  `うちあわせ` 打合せ → **打ち合わせ**（送り仮名つき・標準的）。
- レイテンシ: v3.2 が全件で同等〜高速。日常語20件平均 v3.1=21.5ms → **v3.2=19.8ms（約8%速い）**。難ケースは収束が速く差が大きい。

### 判定

- **v3.2-small ドロップインは低リスクな微positive**（同サイズ70MB・API変更なし・回帰0・たまに品質改善・常に同等以上の速度）。
  ただし改善幅は mild（人工的な難文と送り仮名スタイルが中心）で緊急性はない。
- 採用するなら `keynaco/Resources/` の gguf submodule を v3.2-small に差し替えるだけ（LFS）。
- **本命は右文脈**だが、それは AzooKey アップグレード＋右文脈の配線（カーソル後テキスト）という別プロジェクト。
- 限界: 28ケースは中規模サンプル。回帰0は心強いが網羅ではない。条件付き変換ケースの比較は少数。

## 限界・補足
- 「品質」は top 候補の正誤で評価。N-best 全体の質や体感は見ていない。
- 収束点 ≤3 は試した数ケースの観測。全入力で 3 で十分とは限らないので、デフォルト 5 の安全余裕は妥当。

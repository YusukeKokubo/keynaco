## F1: 変換候補の文脈スコアリング

### 目的

`buildCandidateList()` が返す候補リストを、直前の確定済みテキスト（`surroundingText()`）に照らして
LLM が最も自然と判断した順に並び替える。

### UX

1. Space 押下時は即座に既存ロジックの順で候補ウィンドウを表示する（レイテンシゼロ）
2. LLM のスコアリングが非同期で完了したら、候補ウィンドウをリフレッシュして並び替える
3. ユーザーが既に候補を選択済み（↑↓を押した）の場合はリフレッシュしない（`isExplicitlySelected` チェック）

### プロンプト設計

```
【文脈】<直前の確定テキスト 100 文字>
【読み】<composedHiragana>
【候補】
1. <candidate_0>
2. <candidate_1>
...

最も自然な候補の番号を1つだけ答えてください。
```

- 候補数は上位 10 件に絞る（AzooKey + 高スコア履歴のみ）
- LLM の返答が候補リストの範囲外なら無視し、既存順を維持する

### 実装場所

新規ファイル `Sources/LLMCandidateScorer.swift`

```swift
@MainActor
final class LLMCandidateScorer {
    private var task: Task<Void, Never>?

    func score(
        candidates: [String],
        context: String,
        reading: String,
        onResult: @escaping (Int) -> Void  // 推薦インデックス
    )

    func cancel()
}
```

`InputHandler` は `LLMCandidateScorer` を持たない（UI 依存のため `InputController` 側に置く）。
`InputController` が `handleSpace()` → `buildCandidateList()` 完了後に scorer を起動し、
結果を `candidateWindow.reorder(topIndex:)` に渡す。

### 注意

- `composedHiragana` が変わったら前の scorer タスクをキャンセルする
- 確定（Enter/数字キー）後はキャンセル不要（結果を捨てるだけでよい）

## F2: セグメントモード全文変換提案

### 目的

セグメントモード（Space 長押し or 変換後 Space）で、AzooKey の文節分割結果に加えて、
LLM が `composedHiragana` 全体を一括変換した候補を先頭に1件追加する。

### UX

1. セグメントモード突入時に LLM タスクを起動
2. AzooKey 結果は即時表示（既存）
3. LLM 結果が返ったら候補リストの先頭（インデックス 0）に挿入し、ウィンドウをリフレッシュ
4. 確定時の挙動は他候補と同じ（`commitText` → DB 記録）
5. 挿入後も選択カーソルは元の位置をキープ（リフレッシュ前に選択していた候補のインデックスを +1 補正）

### プロンプト設計

```
次のひらがなを自然な日本語に変換してください。変換結果のテキストだけを出力してください。
<composedHiragana>
```

- 返答が元のひらがなと同じ、または空の場合は挿入しない
- 返答が既存の AzooKey 候補と完全一致する場合も挿入しない（重複回避）

### 実装場所

新規ファイル `Sources/LLMSegmentConverter.swift`

```swift
@MainActor
final class LLMSegmentConverter {
    func convert(
        hiragana: String,
        onResult: @escaping (String) -> Void
    )
    func cancel()
}
```

`InputHandler+SegmentMode.swift` の `enterSegmentMode()` で LLM タスクを起動し、
結果を `InputController` 経由で `candidateWindow` に差し込む。
`InputHandler` は結果文字列をコールバックで受け取るのみ（UI 操作はしない）。

## F3: Successor モードの意味的後続語

### 目的

現状の Successor モードは DB の bi-gram / tri-gram がないと候補が出ない（学習ゼロの冷スタート）。
LLM を使って「意味的に続きやすい語」を補完し、DB に学習がない状態でも候補を返す。

### 発動条件

`suggestSuccessors()` で DB クエリ結果が `immediateThreshold` 未満（保留状態）かつ
格助詞 fallback しか出ない場合、LLM に後続語を問い合わせる。

### プロンプト設計

```
「<lastCommittedWord>」の直後に来る日本語の語（名詞・動詞・形容詞）を5つ挙げてください。
1語ずつ改行で出力してください。助詞は含めないでください。
```

- 返答を行分割し、各語を Successor 候補に追加（`pendingSuccessorCandidates` の末尾へ）
- 既存の bi-gram / tri-gram 候補と重複する語は除外

### 表示タイミング

LLM 結果は非同期で `pendingSuccessorCandidates` に追記するだけ。
ユーザーが1打目を入力した時点（既存の読みフィルタロジック）で評価されるため、
LLM 由来候補かどうかを UX 上で区別する必要はない。

### 実装場所

`InputHandler+SuccessorMode.swift` の `suggestSuccessors()` に
`LLMSuccessorFetcher`（新規クラス）の呼び出しを追加。

```swift
@MainActor
final class LLMSuccessorFetcher {
    func fetch(
        after word: String,
        onResult: @escaping ([String]) -> Void
    )
    func cancel()
}
```

## F4: 誤変換検出

### 目的

確定直後に確定済みテキスト全体を LLM でチェックし、
不自然な箇所があればメニューバーアイコンを変化させてユーザーに気づかせる。

### UX

- 確定後 0.5 秒のデバウンスで起動（高速タイプ中に何度も発火しないよう）
- 問題なし: アイコンは通常（`⌨`）
- 問題あり: アイコンを `⌨?` に変更し、クリックで該当テキストと修正案をポップオーバーで表示
- 次の変換操作が始まったらポップオーバーは自動で閉じる
- 確定テキストが 5 文字未満の場合はスキップ（コスト削減）

### プロンプト設計

```
次の日本語テキストに誤変換や不自然な表現があれば、箇所と修正案を指摘してください。
問題がなければ「OK」とだけ答えてください。
<surroundingText の直前 200 文字>
```

- 返答が「OK」または空なら何もしない
- 返答にテキストがあればポップオーバーに表示

### 実装場所

新規ファイル `Sources/LLMMisconversionChecker.swift`

```swift
@MainActor
final class LLMMisconversionChecker {
    var onIssueFound: ((String) -> Void)?   // 修正案テキスト
    var onClear: (() -> Void)?

    func check(surroundingText: String)
    func cancel()
}
```

`AppDelegate` が `NSStatusItem` とポップオーバーを管理（既存の `⌨` アイコンを流用）。
`InputController` が `insertText` 後に `LLMMisconversionChecker.check()` を呼ぶ。
`Notification` ベースで `AppDelegate` にイベントを伝搬する（既存の Successor 保留通知と同パターン）。

## 共通設計方針

### FoundationModels の可用性チェック

全クラスの初期化時に `SystemLanguageModel.default.availability` を確認し、
`.available` 以外の場合は即 return する（Apple Intelligence 非対応 Mac で無音無害）。

### LanguageModelSession の管理

セッションは各クラスが1インスタンスを `lazy` で保持し、キャンセル時は `task?.cancel()` のみ。
セッション自体は再利用する（`LanguageModelSession` の生成コストを避ける）。

### エラーハンドリング

LLM タスクはすべて `do { ... } catch { }` で握り潰す。
失敗しても既存の変換ロジックが動き続けることが最優先。

### ファイル構成

```
Sources/
  GhostTextEngine.swift     ← 削除
  GhostTextWindow.swift     ← 削除
  LLMCandidateScorer.swift  ← 新規（F1）
  LLMSegmentConverter.swift ← 新規（F2）
  LLMSuccessorFetcher.swift ← 新規（F3）
  LLMMisconversionChecker.swift ← 新規（F4）
```

| 優先 | 理由 |
|------|------|

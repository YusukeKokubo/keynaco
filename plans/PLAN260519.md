# 候補リスト組み立てのセクション宣言化

## 背景

`InputHandler+Candidates.swift` の `assembleCandidateList`（約 80 行）は、
履歴・予測・固定（ひらがな/カタカナ）・ユーザー辞書・Zenzai・数値・日時・
低スコア履歴という **8 種類のセクション** を順序通り並べるロジックを担う。

現在は次のように手続き的なミューテーションで実装されている:

```
1. candidates = highHistory + azooKeyUniq
2. candidates.insert(uniquePredictions, at: 0)
3. candidates.insert(hiragana/katakana, at: 0)    // 条件付き
4. candidates.insert(userDict, at: fixedCount)
5. candidates.insert(zenzaiTop1, at: fixedEnd)    // 条件付き
6. candidates.insert(number, at: historyEnd)
7. candidates.insert(dateTime, at: historyEnd + ...)
8. candidates.append(lowHistory)
```

並行して `fixedCount` → `fixedEnd` → `adjustedFixedEnd` →
`predictionEnd` → `historyEnd` という **5 つの境界インデックス**を
手動で進めている。

## 問題

1. **境界インデックスの整合性が手動管理**
   - 新しいセクションを追加するたびに、後続セクションの位置計算をすべて
     見直す必要がある。off-by-one を生みやすい
   - `fixedEnd = fixedCount + userDictCount` と
     `adjustedFixedEnd = fixedEnd + zenzaiTop1Count` のように
     "派生" インデックスが層をなしていて読み解きにくい

2. **挿入順と表示順が暗黙に結合**
   - L290-293 で `highHistory + azooKeyUniq` から開始し L291 で
     `uniquePredictions` を `at: 0` に挿入する書き方は、
     最終的に `predictions + highHistory + azooKeyUniq` の順を作るための
     **意図せず順序依存** な処理
   - 「Zenzai top-1 を userDict より前に出したい」のような変更が
     ローカルに済まず、複数の境界計算をまたいで影響する

3. **副作用が混入**
   - L340 で `self.lastZenzaiRow` を assembler 内で更新している。
     リスト構築関数が UI ラベル用の state を書き換えるのは責務漏れ

4. **テスト困難**
   - 「数値候補が historyEnd に挿入されているか」を直接検証するには
     `.show` の 5 引数（candidates / historyEnd / initialRow /
     predictionEnd / fixedEnd）を組み合わせて推論するしかない。
     セクションが構造として残っていればテストが書きやすい

## 目的

候補リストの組み立てを **セクションの宣言的な並び** に変換する。

- 各セクションの「中身・優先度・historyEnd に含めるか」をデータとして表現
- 統合層は順序通り並べ・重複排除・境界計算を機械的に実行
- 副作用（`lastZenzaiRow` 更新等）は assembler の外に追い出す
- `CandidateAction.show` の出力契約は変えない（呼び出し側に影響なし）

## 設計

### CandidateSection

```swift
struct CandidateSection {
    enum Kind {
        case prediction       // n-gram 予測
        case fixedHiragana    // ひらがな先頭固定（hiraganaPreferred 時）
        case fixedKatakana    // カタカナ先頭固定（foreign marker 時）
        case userDict         // ユーザー辞書
        case zenzaiTop1       // Zenzai top-1 プロモート
        case highHistory      // 高スコア履歴
        case azooKeyDict      // AzooKey 辞書候補
        case number           // 数値変換
        case dateTime         // 日時変換
        case lowHistory       // 低スコア履歴（末尾）
    }

    let kind: Kind
    let items: [String]
}
```

### 表示順は `[Kind]` の固定配列で宣言

```swift
private static let sectionOrder: [CandidateSection.Kind] = [
    .fixedHiragana, .fixedKatakana,   // 排他: 高々1つ
    .userDict,
    .zenzaiTop1,
    .prediction,
    .highHistory,
    .azooKeyDict,
    .number, .dateTime,
    .lowHistory,
]
```

セクションの並び替え・追加・削除はこの配列を編集するだけで完結する。

### 境界の自動計算

```swift
struct CandidateLayout {
    let candidates: [String]
    let fixedEnd: Int        // .fixedHiragana/.fixedKatakana/.userDict/.zenzaiTop1 の末尾
    let predictionEnd: Int   // fixedEnd + .prediction
    let historyEnd: Int      // predictionEnd + .highHistory
    let initialRow: Int

    /// セクション境界の不変条件を assert
    init(sections: [CandidateSection], ...) {
        // 重複排除しながら連結
        // kind ごとに境界を集計
        // fixedEnd <= predictionEnd <= historyEnd <= candidates.count を保証
    }
}
```

### assembler の責務

```swift
private mutating func assembleCandidateList(
    from sources: CandidateListSources, autoShow: Bool
) -> CandidateAction {
    if shouldDismiss(sources) { return .dismiss }

    let sections = buildSections(from: sources)
    let layout = CandidateLayout(
        sections: sections,
        sectionOrder: Self.sectionOrder,
        initialRowPolicy: makeInitialRowPolicy(sources: sources)
    )
    return .show(
        candidates: layout.candidates,
        historyEnd: layout.historyEnd,
        initialRow: layout.initialRow,
        predictionEnd: layout.predictionEnd,
        fixedEnd: layout.fixedEnd
    )
}
```

### `lastZenzaiRow` の分離

`CandidateAction.show` に `zenzaiRow: Int?` を追加する案と、
`InputHandler` 側で `layout` から `firstIndex(where:)` で
事後計算する案がある。前者の方がコンシューマに優しい。

→ 当面は **post hoc で `layout.indexOf(.zenzaiTop1)` を呼び出し側で計算** する。
   `.show` の契約変更は別 PR で。

## 段階移行プラン

### Step 1: スナップショットテスト（防壁構築）

リファクタ前に **既存挙動のスナップショット** を取る:

- 代表的な 20-30 ケース（履歴あり/なし、Zenzai on/off、
  hiraganaPreferred、foreign marker、autoShow on/off 等）を
  `InputHandlerCandidatesTests` に追加
- 各ケースで `candidates` / `historyEnd` / `predictionEnd` / `fixedEnd` /
  `initialRow` の **完全な値** を assert
- このテストはリファクタ前後で 1 行も書き換えずに通ること

リファクタ単体では新規バグを生まないことの保証になる。

### Step 2: CandidateSection / CandidateLayout 導入

- 新型を追加。既存 assembler は手付かず
- `CandidateLayout` は構造体のみで副作用なし、ユニットテストを書く
  - 不変条件 assert
  - 順序保持・重複排除
  - 境界計算

### Step 3: assembler の書き換え

- `buildSections` で `sources` から `[CandidateSection]` を構築
- `CandidateLayout` に委譲
- Step 1 のスナップショットテストが全部 GREEN のまま通ることを確認

### Step 4: `lastZenzaiRow` 副作用の分離

- assembler から `self.lastZenzaiRow = ...` を除去
- 呼び出し側（candidateAction を返す箇所）で計算

### Step 5: hiraganaPreferred / foreignMarker の優先関係を明示化

- `resolveFixedSlot(reading:) -> FixedSlot { .none, .hiragana, .katakana }`
  を切り出し
- `assembleCandidateList` 内の if/else if 排他をこの関数で表現
- 「`hiraganaPreferred` は `foreignMarker` より強い」をコメントで明示

## 非ゴール

- `CandidateAction.show` の引数追加・削除（別 PR）
- `predictCount` / `highHistoryCount` の意味論変更
- 候補ソース（azooKey・履歴・bigram）取得処理の変更
- パフォーマンス改善（リスト構築は数十要素なので最適化不要）

## リスク

- Step 3 で境界インデックスの計算規則が現行と微妙にずれる可能性
  → Step 1 のスナップショットテストで網羅できれば回避できる
- `lastZenzaiRow` を読んでいる UI コード（候補ウィンドウのラベル描画）の
  挙動が変わらないことを sandbox で確認

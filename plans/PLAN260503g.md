# N-gram few-shot 動的注入

## 目的

`LLMCandidateScorer` が現状「文脈テキスト + 読み + 候補リスト」だけで LLM に判断を委ねている。
ユーザー固有の変換傾向（N-gram DB）を few-shot 例としてプロンプトに注入し、
LLM がそのユーザーらしい候補を選べるようにする。

## 現状の課題

- `buildPrompt` は一般的な日本語判断しかできない
  - 「会議」の後に「を」と「が」どちらが自然かは文体依存だが、LLM はユーザー DB を知らない
- `context: String` は IMK クライアントの生テキスト（最大100文字）であり、
  個人の変換パターンとは別物
- N-gram DB に蓄積された「このユーザーは〇〇の後に△△を好んで使う」という情報が活用されていない

## 方針

`InputController` 側で `committedHistory` の直近語に対する **bi-gram 上位**を取得し、
`score()` へ `examples: [(prev: String, next: String)]` として渡す。
`buildPrompt` でこれを「ユーザー変換傾向」セクションとして候補より前に挿入する。

few-shot 例は **最大5件**（プロンプト肥大化防止）。LLM API への変更はなし。

**tri-gram は few-shot には使わない**: `context: String` には直前テキストがすでに渡っているため、
tri-gram の2語文脈を few-shot に追加しても情報が重複し LLM を混乱させる恐れがある。
tri-gram は将来「候補の事前絞り込み」に使う方向で検討する（このPLANの対象外）。

## 変更箇所

### 1. `LLMCandidateScorer.score()` のシグネチャ変更

```swift
// before
func score(
    candidates: [String],
    context: String,
    reading: String,
    onResult: @escaping (Int) -> Void
)

// after
func score(
    candidates: [String],
    context: String,
    reading: String,
    examples: [(prev: String, next: String)],   // 追加
    onResult: @escaping (Int) -> Void
)
```

### 2. `LLMCandidateScorer.buildPrompt()` の変更

```swift
// before
private static func buildPrompt(context: String, reading: String, candidates: [String]) -> String

// after（internal に昇格してテスト可能にする）
internal static func buildPrompt(
    context: String,
    reading: String,
    candidates: [String],
    examples: [(prev: String, next: String)]
) -> String
```

プロンプト構造:

```
【このユーザーの変換傾向】（examples が空でないときのみ出力）
- 「資料」の後 → 「作成」
- 「会議」の後 → 「議事録」
...（最大5件）

【文脈】〇〇
【読み】〇〇
【候補】
1. 〇〇
2. 〇〇
...

最も自然な候補の番号を1つだけ答えてください。
```

### 3. `InputController` の呼び出し側変更

`score()` を呼ぶ箇所（L360付近）で、`committedHistory` の直近2語から few-shot 例を構築する。

```swift
// bi-gram から examples を構築
var seen = Set<String>()
var examples: [(prev: String, next: String)] = []
if let lastWord = handler.committedHistory.last {
    let bigramTop = db.fetchBigramTop(prev: lastWord, limit: 5)
    for next in bigramTop where seen.insert(next).inserted {
        examples.append((prev: lastWord, next: next))
    }
}
// tri-gram は few-shot には使わない（context: String と重複するため）

// score 呼び出し
Self.candidateScorer.score(
    candidates: opts,
    context: contextPrefix,
    reading: reading,
    examples: examples
) { [weak self] idx in ... }
```

`db` は `InputController` が `handler.db` として参照できる（`InputHandler` の `db` は `internal`）。

## テスト方針

- `buildPrompt(context:reading:candidates:examples:)` を `internal` に変更し、`@testable import` で直接テスト
- テストケース
  - `examples` が空 → 「ユーザー変換傾向」セクションが出力されない
  - `examples` が1件以上 → セクションヘッダーと各行が正しく出力される
  - `examples` が5件になる（`fetchBigramTop(limit: 5)` で上限保証）
- `score()` の LLM 呼び出し自体はオンデバイス LLM 依存のため単体テスト対象外

## 実装順序

1. `buildPrompt` を `internal` に変更 + `examples` 引数追加 + 出力フォーマット変更
2. `score()` に `examples` 引数追加（既存呼び出し箇所はコンパイルエラーになるので同時修正）
3. `InputController` で N-gram 例を構築して `score()` に渡す
4. `buildPrompt` の単体テスト追加
5. 動作確認（EventViewerWindow でキャプチャ比較、few-shot あり/なしで選択結果の差分を確認）

# POC260524: history.db からの Zenzai パラメーター自動推論

## 背景・動機

Zenzai（zenz-v3）は `profile`・`topic`・`style`・`preference` の制御パラメーターを受け付け、変換確率分布を文脈に合わせてバイアスできる。keynaco の設定 UI にこれらの項目を追加したが、実際の使い方と合わない問題がある。

- 文書の種類・話題は場面ごとに変わる（仕事のメール、コード、SNS 投稿…）
- ユーザーが都度設定を変えるのは非現実的
- 一方、`leftSideContext`（直前の入力文字列）はすでに渡しており、ある程度は文脈適応している

## やりたいこと

**ユーザーの直近の入力から「今どんな文章を書いているか」を自動推論し、Zenzai パラメーターに動的に反映する。**

### 使えるデータ

- `LLMPOSClassifier` が `proper_noun` を分類済みで history.db に蓄積されている
- 固有名詞は話題の指標になる（`TypeScript`・`React` が多い → 技術文書。`田中部長`・`会議` が多い → ビジネス文書）

### 基本的な流れ（案）

```
history.db から直近 N 件の proper_noun を頻度順に取得
→ 上位 3〜5 件をカンマ区切りで topic に詰める（25 字以内）
→ ユーザーの手動設定が空のパラメーターにだけ自動補完
→ converter 再生成タイミング（設定変更・一定時間経過）で更新
```

### ユーザー設定との関係

| 状態 | 動作 |
|------|------|
| ユーザーが topic を手動設定済み | 手動設定を優先（自動補完しない） |
| topic が空 | 自動推論した値を使う |
| proper_noun の蓄積が少ない | 空のまま（フォールバック） |

## 探りたいこと

1. **効果の有無**: 自動推論した topic を渡すと変換候補が体感できるレベルで変わるか
2. **推論の質**: 直近固有名詞をそのまま topic に渡すだけで十分か、頻度重み付けや分類が必要か
3. **タイミング**: 変換リクエストごとに DB クエリするのは重いか。`AzooKeyConverter` の再生成単位で更新すれば十分か
4. **混在ノイズ**: 異なる話題の固有名詞が混在したとき（例: `TypeScript,田中部長,居酒屋`）、有害なバイアスになるか中立になるか

## 最小 PoC の実装イメージ

`ZenzaiSettings.makeConverter()` の中で topic が空なら DB から直近固有名詞を引いて渡すだけ。

```swift
// ZenzaiSettings.makeConverter() 内
let topic: String
let manualTopic = d.string(forKey: topicKey) ?? ""
if manualTopic.isEmpty {
    let recentNouns = DatabaseManager.shared.recentProperNouns(limit: 5)
    topic = String(recentNouns.joined(separator: ",").prefix(25))
} else {
    topic = manualTopic
}
```

## 未検討の論点

- `profile` / `style` / `preference` にも同様の自動推論を適用するか（topic だけで十分かもしれない）
- アプリ連動（フロントアプリの BundleID ごとに履歴を分ける）との組み合わせ
- 自動推論の結果をデバッグ UI（IMESandboxWindow）で可視化する

## 検証結果（2026-05-24）

### 実装した内容

- `DatabaseManager.recentProperNouns(limit:)` を追加（`pos LIKE 'proper_noun%'` を `MAX(used_at) DESC` で取得）
- `ZenzaiSettings.makeConverter()` で `manualTopic` が空のとき DB から自動補完するよう実装

### 発見1: leftSideContext の効果は明確かつ強力

`/keynaco-ime-sandbox` で確認した文脈依存変換の結果：

| 入力 | leftSideContext | fixedEnd | top 候補 |
|------|----------------|----------|---------|
| すいふと | なし | 0 | スイフト, すいふと, SWIFT |
| すいふと | "Python, JavaScript, TypeScript を使って" | 1 | **SWIFT**（Zenzai プロモート） |
| じゃば | なし | 0 | Java, ジャバ |
| じゃば | "Javaでサーバーサイドを実装している。" | 1 | **Java**（Zenzai プロモート） |
| じゃば | "蛇が庭に出た。大きな" | 1 | **蛇場, 蛇ば**（蛇文脈にバイアス） |

→ `leftSideContext` だけで同音異義語の disambiguation は十分に機能している。`topic` の追加効果を測る前に、leftSideContext がほぼ正解を返している。

### 発見2: 実際に渡されている topic はノイズだらけ

現状の history.db の proper_noun 上位5件（`MAX(used_at) DESC`）：

| output | 正誤 |
|--------|------|
| 入力 | ❌ 誤分類（common noun） |
| 固有名詞 | ❌ 誤分類（common noun） |
| claude | ✅ |
| 情報が | ❌ 誤分類（"情報が" は助詞付き） |
| 東京タワー | ✅ |

実際に Zenzai に渡されている topic = `"入力,固有名詞,claude,情報が,東京タワー"`（24字）。有用な固有名詞は "claude" と "東京タワー" のみで、残りはノイズ。

**根本原因**: `LLMPOSClassifier` の誤分類率が高い。テスト入力として "入力" "固有名詞" "情報が" などを繰り返し打ったことで、これらが `proper_noun/place` と誤分類されて蓄積されている。

### 結論・方針転換

| 問い | 結果 |
|------|------|
| topic 自動推論は効果があるか | **leftSideContext で十分**。topic の追加効果を単独で確認できなかった |
| 直近固有名詞をそのまま渡すだけで十分か | **不十分**。誤分類ノイズが上位を占め、有害なバイアスになる可能性がある |
| 混在ノイズは問題か | **問題あり**。topic が `"入力,固有名詞,..."` では何もバイアスしていないか逆効果の可能性 |

### 次に取り組むべきこと

1. **POS 分類精度の改善が先決**: 誤分類を減らさないと proper_noun からの推論は使えない。具体的には：
   - `pos_retry=true` になっている低信頼度エントリを除外する
   - 助詞付き（`情報が` 等）エントリを `proper_noun` 候補から除外（output に助詞を含む場合フィルター）
   - `proper_noun/person` / `proper_noun/org` / `proper_noun/place` の subcategory 限定でフィルター
2. **topic の ROI 再評価**: leftSideContext が十分に機能している現状では、topic 自動推論のコストが見合うか疑問。まず POS 精度改善を優先し、クリーンなデータでの効果を再測定する

## 改善実装（2026-05-24 続き）

### 実装した修正

**1. `recentProperNouns` のフィルタリング強化**
- `pos IN ('proper_noun/place', 'proper_noun/person', 'proper_noun/org')` のみ（bare `proper_noun` 除外）
- `pos_retry = 0` のみ（低信頼度除外）
- Swift 側で助詞サフィックス（が・を・は・に・で・へ・と・の・から・まで・より・など・て・も）のチェックを追加

**2. LLM プロンプトの改善**
- `"No explanation"` 指示追加（説明文返答の抑制）
- `proper_noun` の定義を明確化（"real-world named entity"）
- 誤分類されていた語の negative example を追加: `入力 → noun/suru:high`, `固有名詞 → noun/common:high`, `地名 → noun/common:high`

**3. DB マイグレーション追加**
- `:confidence` なし旧形式 pos_tag のエントリを `pos_retry = 1` に更新 → 次回確定時に新プロンプトで再分類される

### マイグレーション後の DB 状態

| エントリ | pos_retry 変化 | 備考 |
|---------|---------------|------|
| `東京タワー` | 0 → **1** | 再分類待ち（新プロンプトで正しく分類される見込み） |
| `情報が` | 0 → **1** | 再分類待ち（かつ助詞フィルターで除外） |
| `地名` | 0 → **1** | 再分類待ち |
| `固有名詞` | 0 → 0（変化なし） | `proper_noun/org:high` で `:` があるため migration の対象外（false negative）。開発時テスト入力の残留で通常使用では発生しない |

### 現状の `recentProperNouns(limit: 5)` が返す値

マイグレーション後、`pos_retry=0` かつ subcategory 付きのエントリは `固有名詞` のみ。`東京タワー` は pos_retry=1 になったため除外され、次回の確定・再分類後に復帰する。

### 残課題

- クリーンなデータ（正常使用後）での topic 効果を再測定する必要がある
- `固有名詞` が false negative として残っているが、通常使用では発生しない開発時アーティファクト

## プロンプト改善の副作用と設計上の気づき（2026-05-24 続き）

### 発見: バックフィル再分類でプロンプト変更が逆効果になった

新プロンプト（"No explanation" 追加・負例を大量追加）を適用後、`performPOSBackfill` が "東京タワー" を再分類した結果が `noun|noun|pos_retry=1` に退行。

**原因**: `performPOSBackfill` はコンテキストなしで一括分類（line 55: `posClassifier.classify(output: output)`)。Apple Intelligence の小型オンデバイスモデルは、コンテキストなし + プロンプトが長い・複雑な場合、固有名詞を "noun" と返す不安定さがある。

**プロンプトの教訓**: 小型オンデバイスモデルは例が多いほど良いわけではない。元の構造（例の数を絞る）に戻しつつ、最重要な負例（入力・固有名詞）のみ追加する形に収束した。

### 発見: フィルターの保守性が正しく機能している

- "東京タワー" が `pos_retry=1`（= 信頼度不足）になる → `recentProperNouns` から除外 ✅
- 次に実際の確定時（コンテキストあり）に正しく再分類される → フィルターを通って topic に追加される ✅

バックフィルが不安定でも、`pos_retry=0` のエントリしか使わないフィルターが安全弁として機能している。設計上正しく動いている。

### バックフィルの根本的限界

`performPOSBackfill` はコンテキストなし一括分類のため、固有名詞（特に地名・人名）の正確な再分類には不向き。`schedulePOSClassification`（実際の確定時・コンテキストあり）の結果が信頼できるデータとなる。

→ **topic 自動推論の実用性は「実際の使用で蓄積されたコンテキスト付き分類データ」に依存する。バックフィルで事前に整備しようとするアプローチは限界がある。**

## シミュレーション実測（2026-05-24 最終）

### 方法

`Swift`, `GitHub`, `Xcode`, `Apple`, `SwiftUI` を正しく分類された固有名詞として DB に直接 INSERT し、keynaco を再起動（`makeConverter()` が topic=`"Swift,GitHub,Xcode,Apple,"` を取得する状態）。

**A**: inMemoryDB（topic=空）  
**B**: realDB（topic=`Swift,GitHub,Xcode,Apple,`）

2パターンのテスト：
- `leftSideContext="今日は"` あり（8単語）
- `leftSideContext` なし（topic 単体の効果を分離）

### 結果

**すべてのケースで A と B に差異なし。fixedEnd=0（Zenzai プロモートなし）も全ケース同じ。**

| 入力 | A top候補 | B top候補 | 差 |
|------|----------|----------|-----|
| すいふと | すいふと,スイフト,SWIFT | すいふと,スイフト,SWIFT | なし |
| じゃば | Java,ジャバ,JABA | Java,ジャバ,JABA | なし |
| こーど | コード,Code | コード,Code | なし |
| ぎっと | git,ギット | git,ギット | なし |
| あっぷる | Apple,アップル | Apple,アップル | なし |
| らいぶらり | ライブラリ | ライブラリ | なし |
| こんぱいらー | コンパイラ | コンパイラ | なし |

### 最終結論

**topic パラメーターは zenz-v3.1-small において測定可能な変換品質の差をもたらさない。**

- `leftSideContext` が支配的（文脈なし→fixedEnd=0、技術文脈あり→fixedEnd=1）
- topic は leftSideContext なしでも効果を確認できなかった
- 自動推論のコスト（DB クエリ + POS 分類品質問題）に見合う利益がない

### 判断

**topic 自動推論コードは現状維持（削除しない）が、これ以上 ROI を投じない。**

理由：
- コードは動いており害はない
- 将来 zenz-v3 の上位モデルや異なる入力パターンで効果が出る可能性はゼロではない
- ただし現在の zenz-v3.1-small + keynaco の使用パターンでは `leftSideContext` が十分

**本 POC はクローズ。**

## 追加検証: 抽象ワード topic の効果（2026-05-24）

### 背景

Gemini からの考察として「具体的固有名詞ではなく `IT` や `IT,プログラミング,技術` のような抽象ワードを topic に指定すれば small モデルでも効くかもしれない」という仮説が提示されたため追加検証した。

### 方法

`defaults write` で topic を書き換え → `{"reset": true}` でコンバーター再生成（keynaco 再起動不要）。  
`leftSideContext` なし・inMemoryDB で 4 条件を比較。

| 条件 | topic 値 |
|------|---------|
| A | `""` （空） |
| B | `"IT"` |
| C | `"IT,プログラミング,技術"` |
| D | `"Swift,GitHub,Xcode,Apple"` （POC 再現） |

### 結果

| 入力 | A | B | C | D |
|------|---|---|---|---|
| すいふと | すいふと, スイフト, SWIFT | スイフト, SWIFT, すいふと | **SWIFT**, スイフト, すいふと | すいふと, SWIFT, スイフト |
| じゃば | Java, ジャバ | Java, ジャバ | Java, ジャバ | Java, ジャバ |
| こーど (fixedEnd=1) | コード, Code | コード, Code | コード, Code | コード, Code |
| ぎっと | git, ギット | git, ギット | git, ギット | git, ギット |
| あっぷる | Apple, アップル | Apple, アップル | Apple, アップル | Apple, アップル |

全条件で `fixedEnd=0`（Zenzai プロモートなし）。「すいふと」の top 候補順位に微細な変動はあったが fixedEnd は変化せず、Zenzai 自体は topic に反応していない。

### 結論

抽象ワード topic でも結果は変わらない。**Gemini の仮説は否定された。** POC のクローズ判断を再確認。

# PLAN260429b: 学習強化 — 使えば使うほどタイプ数が減る

## 背景・目的

「使えば使うほどタイプ数を少なくできる」IME を目指す。
コード調査の結果、現状の学習基盤（bi-gram / tri-gram / history count）は正しく動作しているが、
以下の 3 点で体験が改善できる。

---

## 改善 A: 候補スコアリング（現状確認 → 後回し）

### 調査結果

- `commitText()` で `recordBigram` / `recordTrigram` を毎確定時に呼んでいる → 記録 OK
- `fetchHistoryExact` / `fetchHistoryPrefix` は `count DESC, used_at DESC` でソート → OK
- 候補リスト順: 予測（tri-gram > bi-gram）→ 履歴 exact → 履歴 prefix → AzooKey

スコアリング自体は既に機能している。B・D の実装後に様子を見て追加改善を判断する。

---

## 改善 B: Successor チェーンの解禁

### 現状の問題

`suggestSuccessors()` に「直前確定が格助詞なら表示しない」チェックがあり、
格助詞確定後に次の Successor が起動しない。

```swift
// InputHandler+SuccessorMode.swift
if InputHandler.particles.contains(last) {
    isSuccessorMode = false; successorFirstChar = nil
    return .dismiss
}
```

また `handleSuccessorMode` の確定後は `.dismiss` 固定で、Successor 内で格助詞を選んでも
次の連想が表示されない。

### 目標

「東京」→（Successor）→「が」→（Successor）→「好き」という連鎖確定を可能にする。

### 無限ループの安全性

`confirmSuccessor` 内で `recordBigram` が呼ばれるため、「が」→「を」のような格助詞連続選択を
すると格助詞間 bi-gram が実際に学習される。ただし `isNounLike("が") = false`（ひらがな末尾）
なので `particlesFallback` が付かず、格助詞の後の Successor 候補は bi-gram/tri-gram に
学習済みの語がある場合のみ表示される。意図的に格助詞→格助詞を繰り返し確定しない限り
候補リストが空になって自然に `.dismiss` になる。

### 変更箇所

**1. `InputHandler+SuccessorMode.swift` — 格助詞チェック削除**

```swift
// 削除（3行）:
if InputHandler.particles.contains(last) {
    isSuccessorMode = false; successorFirstChar = nil
    return .dismiss
}
```

**2. `InputHandler+SuccessorMode.swift` — 確定後に次の Successor を起動**

`handleSuccessorMode` の Space/Enter 分岐:

```swift
// 変更前:
confirmSuccessor(selected, client: client)
return (true, .dismiss)

// 変更後:
confirmSuccessor(selected, client: client)
return (true, suggestSuccessors())
```

### テストシナリオ

- 「東京」→ Successor で「が」選択 → 学習ゼロの初回は `.dismiss`（OK）
- 数回学習後: 「東京」→「が」→「好き」が Successor で連鎖して確定できる

## 改善 D: 読み省略パターンの自動学習

### 現状の動作

- 「とうきょう → 東京」確定 → `record(input: "とうきょう", output: "東京")`
- 「とうき」で prefix 候補の「東京」を選択 → `record(input: "とうき", output: "東京")`
- 次回「とうき」で exact ヒット → 先頭に出る

この仕組みは**既に動いているが**、ユーザーが意図的に短い読みで選ぶ操作が必要。
フル読みを打ち続けても自動的に短縮は進まない。

### 目標

フル読みで確定するたびに、より短い prefix でも次第に候補が出るようにする。
ユーザーが短縮を意識しなくても、使い続けるだけで自然に短縮が進む。

### 実装方針

**`DatabaseManager` に `recordPrefixes(reading:output:)` を追加する**

- 読みが5文字以上の場合、先頭2文字〜(N-1)文字の各 prefix でも `record` を呼ぶ
- `record` 内の `ON CONFLICT → count += 1` がそのまま効く
- ASCII のみの読みは対象外（英字単語モード）

```swift
// DatabaseManager.swift に追加
func recordPrefixes(reading: String, output: String) {
    record(input: reading, output: output)
    guard !reading.allSatisfy({ $0.isASCII }) else { return }
    let chars = Array(reading)
    guard chars.count >= 5 else { return }
    for len in 2..<chars.count {
        record(input: String(chars.prefix(len)), output: output)
    }
}
```

**`db.record` を `db.recordPrefixes` に置き換える箇所**

| ファイル | メソッド | 対象 |
|---------|---------|------|
| `InputHandler.swift` | `commitComposition` (通常・セグメント) | 全確定パス |
| `InputHandler+Candidates.swift` | `doConfirmSelection` | 候補選択確定 |
| `InputHandler.swift` | `handleFunctionKey` | F6–F10 確定 |
| `InputHandler+SuccessorMode.swift` | `confirmSuccessor` | Successor 確定 |

※ Successor 確定（格助詞など）は読みが短いため `chars.count >= 5` 条件で自然にスキップされる。

### 副作用と許容範囲

- 「とうきょう → 東京」を10回確定すると「とうきょ → 東京」も count=10 になる。
  「とうきょ」で「東京」が先頭に出るようになる → **意図した動作**。
- DB サイズ: N文字の読み → full 1件 + prefixes (N-2)件 = 合計 N-1件/確定。
  読み平均6文字なら約5件/確定。許容範囲。
- 「とうきょく」のような別語と競合するが、別語を選べばその count が上がり自然に解消する。

### テストシナリオ

1. `record(input: "とうきょう", output: "東京")` の代わりに `recordPrefixes` を呼ぶ
2. DB に `(input="とうきょう")` `(input="とうきょ")` `(input="とうき")` `(input="とう")` の各行が存在すること（`count >= 1`）
   ※ `len` は `2..<chars.count` のため `len=1`（"と"）はループ対象外で記録されない
3. 「とうき」だけで fetchHistoryExact に「東京」が返ること

# PLAN260621b: 直近確定の recency 重みを強化して Z1 を上回るランクで出す

## 目的軸

UX-pain 削減。`pain rate`（BS≥2 or scroll>0 or composition_ms>3000）と
`UX 損失 divergence` 件数を下げる。

## ベースライン数値

`/tmp/perf-cycle-260621b-uxpain-baseline-*.txt` から抜粋。サンプル: 16 セッション / 106 確定。

| 指標 | 値 |
|---|---|
| pain rate | 13.2% (14/106) |
| UX 損失 divergence | 4 件（はし/かな/つくるのではなく/つくりたい） |
| scroll≥4 ケース | はし(12), けいそく(7), かな(7), やってみて(4) |
| 1 位確定率 | 70.4% |
| 選択行 p95 | 2 |

### pain 14 件の分類

| パターン | 件数 | 例 |
|---|---|---|
| Z1 が漢字、ユーザーはひらがな確定 | 4 | つくるのではなく / つくりたい / やってみて |
| 2 文字読み同音異義の初回確定（履歴未登録） | 1 | はし→椅 |
| Z1 が違う漢字を推した | 2-3 | けいそく→計測, かな→仮名 |
| composition_ms ≥3 秒だが BS/scroll なし（思考時間） | 6-7 | かいぜんけっか, かくにん など |

## 仮説

### 観測

- `DatabaseManager` に既に時間減衰 recency が実装されとる:
  `recencyExpr = count / (1 + (now - used_at) / tau)`, `tau = 30 日`
- 新規確定（count=1）のスコアは ~1.0、30 日前の 1 確定はスコア 0.5
- Zenzai 推論はモデル学習データに支えられて**常に強いスコア**で Z1 を推す
- → **count=1 の新規履歴が頻繁に Z1 に負ける**ため、直近の選択変更が次回以降に反映されにくい

### 仮説

**Z1 が「異なる候補」を推したとき、ユーザーが直近に違うものを確定しとったら、
そっちを優先的に出す**べき。現在の tau=30 日は「累積学習」用には妥当だが、
**「直近の好み変化」を強く反映する設計になっとらん**。

→ recency の重みを強化することで、直近確定（漢字・ひらがな問わず）が Z1 を
上回るランクで出る経路を作る。

### 予測

- `UX 損失 divergence`: 4 → 1-2 件
- `pain rate`: 13.2% → 9-10% 台
- `scroll≥4` ケース: つくる系・やってみて系・けいそく リピートが消える
- 'はし'→'椅' の **初回は救えん**が、2 回目以降の同一ケースは消える

### 副次効果の予想

- **positive**: 1 位確定率が上がる（直近確定の累積で 70% → 75%+ を予測）
- **negative**: たまに使う単語（年数回確定）が見えにくくなる可能性。
  ただし 2 段 decay 設計（下記 候補 2）なら回避可能
- **negative**: 直近の誤確定が次回まで尾を引く。これは現状でも同じ問題

## 構造的 vs 可変の判定

| 観測 | 構造的 / 可変 | 理由 |
|---|---|---|
| Z1 推論の漢字バイアス自体 | **構造的** | Zenzai モデル由来。触らん |
| recency tau / decay 形状 | **可変** | `DatabaseManager.recencyTauSeconds` の定数 + SQL 表現 |
| 'はし' 初回確定の救済 | **構造的** | 履歴がないから不可。許容する |

**可変な部分（recency 重み付け）に絞って動かす**。

## 実装方針（Step 4 で絞る）

レバーを 3 つ検討し、最小副作用のものを選ぶ：

1. **`tau` を短くする** (30d → 7d): 1 行変更でシンプル。ただし累積学習の効きも弱まる
2. **2 段 decay**: 直近 24h 以内に bonus 倍率（例: ×3）、それ以降は従来の 30 日 tau
   - SQL の `recencyExpr` を CASE 式にする
   - 累積学習を壊さんで直近を強める
3. **`count` の重み付け再設計**: SUM じゃなく weighted SUM（直近 confirm に重み）
   - schema 変更（confirm 毎に行を持つ等）が必要なら過剰実装

**候補 2 が最有力**。tau 短縮の単純化と累積学習の維持を両立できる。
ただし `recencyExpr` を呼ぶクエリが 5-6 箇所あるため、CASE 式の置換 or
ヘルパー関数の作り直しが必要。

実装時に副作用範囲を確認してから選ぶ。

## 仮説の弱点（plan 内自己レビュー）

- recency 強化は **過去に同じ確定をしとる場合のみ**効く。ベースライン 14 件のうち
  3-4 件は「初回確定」or「リピートしてない単語」で、推定 8-9 件が直接救えるレンジ
- 「2 段 decay」は 5-6 箇所の SQL 表現を一斉変更する必要があり、回帰リスクが
  ある。回帰テストでカバーしきれん可能性
- 24h window で測れる効果は **過去 24h 内のリピート行動** が母数。実環境では
  日跨ぎの累積効果のほうが大きいかもしれず、24h 観測では効果を過小評価する可能性

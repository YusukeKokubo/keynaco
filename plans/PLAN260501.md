## 改善 E: 文節 Space 確定でフレーズ全体を学習 ✅ `a55c901`

### 現状の問題

`InputHandler+SegmentMode.swift:185 doConfirmSegments`：

```swift
for seg in segmentState.segments {
    db.record(input: seg.reading, output: seg.selectedText)
    azooKeyConverter.commit(reading: seg.reading, text: seg.selectedText)
    confirmed += seg.selectedText
}
commitText(text: confirmed, client: client)
```

問題は2つ：

1. 各文節を個別に `db.record` するだけで、合成読み × 合成出力（例：`きょうはよいてんきです` → `今日は良い天気です`）が1エントリとして残らない。
2. `record` を呼んでおり `recordPrefixes` ではない。PLAN260429b で導入した prefix 学習が **セグメント経路だけ漏れている**。

`commitComposition` のセグメント強制確定分岐（`InputHandler.swift:175–186`）も同じ作りで同じ問題を抱える。

### 目標

- セグメント Space 確定でも「合成読み × 合成出力」を1エントリ学習する。
- 各文節単独でも prefix 学習を走らせる（PLAN260429b と同じ扱い）。

### 変更箇所

**`InputHandler+SegmentMode.swift` `doConfirmSegments`**:

```swift
mutating func doConfirmSegments(candidate: CandidateContext, client: TextInputClient) -> CandidateAction {
    syncFocusedSegmentSelection(from: candidate)
    guard let segmentState = state.segmentState else { return .none }
    var confirmed = ""
    var fullReading = ""
    for seg in segmentState.segments {
        db.recordPrefixes(reading: seg.reading, output: seg.selectedText)  // record → recordPrefixes
        azooKeyConverter.commit(reading: seg.reading, text: seg.selectedText)
        confirmed += seg.selectedText
        fullReading += seg.reading
    }
    if segmentState.segments.count >= 2 {
        db.recordPrefixes(reading: fullReading, output: confirmed)  // ★追加: フレーズ単位
    }
    commitText(text: confirmed, client: client)
    return suggestSuccessors()
}
```

**`InputHandler.swift` `commitComposition` のセグメント分岐**：同様に `record` → `recordPrefixes` に置換し、`segments.count >= 2` のとき合成読み × 合成出力を `recordPrefixes` する。

### 副作用

- 5セグメントの長文を確定すると DB に `(合成読み, 合成出力)` + 各セグメントの prefix 群（合計 N 行/確定）が増える。
- `commitText` 内の bigram/trigram 記録は `state.finalizedText`（合成読み）を使うため、`(prev_word, 合成読み, 合成出力)` という長尺 bigram が記録される。意図通り。

### テスト

- 「きょう」「は」「よい」「てんき」「です」の5セグメントを Space 確定 → DB に `(きょうはよいてんきです, 今日は良い天気です)` `count=1` が存在
- 同時に `(きょうはよいてんきで, 今日は良い天気です)` 等の prefix 群も存在
- 1セグメント単独 Space 確定では合成エントリは記録しない（`segments.count >= 2` ガード）

## 改善 F: recordPrefixes の閾値を 5 → 3 に下げる ✅ `2385023`

### 現状

`DatabaseManager.swift:325`:

```swift
guard chars.count >= 5 else { return }
for len in 2..<chars.count { ... }
```

5文字未満は full 読みのみ。`おはよう`(4) `ありがと`(4) `ぜんぶ`(3) `くるま`(3) など頻出語の prefix が学習されない。

### 目標

3文字以上で prefix 記録を有効化。最短 prefix 長は引き続き 2（`for len in 2..<chars.count`）なので 1文字 prefix の暴発はない。

### 変更箇所

```swift
- guard chars.count >= 5 else { return }
+ guard chars.count >= 3 else { return }
```

### 副作用

- DB 行数増。読み3文字なら +1 行、読み6文字なら +4 行/確定。許容範囲。
- 「とう」(2-char prefix) のような短い読みでヒット数が増え、誤学習が目立つ可能性。これは改善 G の recency で吸収する。

### テスト

- 「おはよう」（4文字）を確定 → `(おはよう, おはよう)` `(おは, おはよう)` `(おはよ, おはよう)` の3行が存在
- 「ぜんぶ」（3文字）を確定 → `(ぜんぶ, ぜんぶ)` `(ぜん, ぜんぶ)` の2行が存在
- 「とう」（2文字）を確定 → `(とう, とう)` のみ（変更なし）

## 改善 G: 時間減衰スコアリング（recency） ✅ `d4a5c98`

### 現状の問題

全 fetch 系の SQL は `ORDER BY count DESC, used_at DESC`。count が支配的で recency はタイブレーカーのみ。半年前の高頻度語が今日の語を抑え込む。プロジェクト名・人名のように「今のタスクで急に頻繁に出る固有名詞」が上位に来るまで時間がかかる。

### 目標

`score = count / (1 + age_days / τ)` の連続スコアで recency を組み込む。τ = 30日（30日経過で count の重みが半減）。閾値ジャンプを避けるため連続関数を採用。

### 設計

**`DatabaseManager` に時間減衰の共通定数と clock 注入を追加**：

```swift
class DatabaseManager {
    private static let recencyTauSeconds: Double = 30 * 86400  // 30日
    var clock: () -> Int64 = { Int64(Date().timeIntervalSince1970) }
    private func nowEpoch() -> Int64 { clock() }
    ...
}
```

`clock` は var にしてテストから差し替え可能にする（Swift 6 strict concurrency 対応のため `@unchecked Sendable` または DI コンストラクタ経由を要検討）。

**全 fetch SQL を score-based ORDER BY に書き換え**：

```swift
// 例: fetchHistoryExact
func fetchHistoryExact(reading: String) -> [String] {
    let now = nowEpoch()
    return queryStrings("""
    SELECT output FROM history
    WHERE input = ? COLLATE NOCASE
    ORDER BY (count * 1.0 / (1.0 + (? - used_at) * 1.0 / ?)) DESC, used_at DESC
    LIMIT 10
    """) { stmt in
        bindText(stmt, 1, reading)
        sqlite3_bind_int64(stmt, 2, now)
        sqlite3_bind_double(stmt, 3, Self.recencyTauSeconds)
    }
}
```

`SUM(count)` を持つ Top 系（`fetchBigramTop` `fetchTrigramTop`）も同様に：

```swift
ORDER BY SUM(count * 1.0 / (1.0 + (? - used_at) * 1.0 / ?)) DESC, MAX(used_at) DESC
```

### 対象メソッド

| ファイル | メソッド | 種類 |
|---------|---------|------|
| `DatabaseManager.swift` | `fetchHistoryExact` | 単純 |
| `DatabaseManager.swift` | `fetchHistoryPrefix` | 単純 |
| `DatabaseManager.swift` | `fetchBigram` | 単純 |
| `DatabaseManager.swift` | `fetchBigramTop` | SUM |
| `DatabaseManager.swift` | `fetchBigramInList` | 単純 |
| `DatabaseManager.swift` | `fetchTrigram` | 単純 |
| `DatabaseManager.swift` | `fetchTrigramTop` | SUM |
| `DatabaseManager.swift` | `fetchTrigramInList` | 単純 |

設定画面用の `fetchAllBigrams` `fetchAllHistory` は count DESC のままで良い（ユーザーに見せる一覧のため学習意図が違う）。

### テストの安定性

記録直後に fetch するテストでは `now - used_at ≈ 0` のため `score ≈ count`。既存テストの相対順序は変わらない。

recency 効果を直接検証するテストでは `db.clock` を未来時刻に固定する：

```swift
db.clock = { fixedNow }
// 記録 ...
db.clock = { fixedNow + 60 * 86400 }  // 60日後
// 別の記録を直近に追加
// fetch 結果を検証
```

### テスト

- 同 count なら直近の方が上位
- count=10 / 30日前 (score≈5.0) と count=3 / 直近 (score=3.0) → 前者が上位
- count=10 / 60日前 (score≈3.33) と count=4 / 直近 (score=4.0) → 後者が上位

## 改善 H: skip-bigram（助詞をまたぐ語間学習） ✅ `f01eee2`

### 現状の問題

`commitText`（`InputHandler.swift:202`）の bigram は直前1語のみ：

```swift
if let p1 = lastCommittedOutput {
    db.recordBigram(prev: p1, input: state.finalizedText, output: text)
    if let p2 = prev2Output { db.recordTrigram(...) }
}
```

`今日 → を → 行く` `今日 → が → 行く` `今日 → も → 行く` は別 bigram に分散し、どれも `今日 → 行く` の学習として効かない。content word ペアの関連が助詞で分断される。

### 目標

助詞を1語スキップした content word 同士の bigram を別テーブル `skip_bigram` に並行記録し、Successor / 予測候補に追加ソースとして提供する。

### 設計

**`committedHistory` を 2 → 5 件に拡張**（`InputHandler.swift:70`）：

```swift
mutating func pushCommitted(_ text: String) {
    committedHistory.append(text)
    if committedHistory.count > 5 { committedHistory.removeFirst() }
}
```

既存の `lastCommittedOutput` `prev2Output` は末尾参照なので影響なし。

**`mostRecentContentWord()` ヘルパー** を `InputHandler` に追加：committedHistory の末尾2件目以降を遡り、`InputHandler.particles` に含まれない最初の語を返す。見つからなければ nil。

```swift
func mostRecentContentWord() -> String? {
    guard committedHistory.count >= 2 else { return nil }
    for i in stride(from: committedHistory.count - 2, through: 0, by: -1) {
        let w = committedHistory[i]
        if !InputHandler.particles.contains(w) { return w }
    }
    return nil
}
```

**新テーブル `skip_bigram`**（`DatabaseManager.swift createTables`）：

```sql
CREATE TABLE IF NOT EXISTS skip_bigram (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    prev    TEXT    NOT NULL,
    input   TEXT    NOT NULL,
    output  TEXT    NOT NULL,
    count   INTEGER NOT NULL DEFAULT 1,
    used_at INTEGER NOT NULL,
    UNIQUE(prev, input, output)
);
CREATE INDEX IF NOT EXISTS idx_skip_bigram ON skip_bigram(prev, input);
```

`recordSkipBigram` `fetchSkipBigram` `fetchSkipBigramTop` を bigram と同シグネチャで追加。

**記録ロジック**（`commitText`）：直前語 `p1` が `particles` に含まれるとき限定で発火。

```swift
if let p1 = lastCommittedOutput {
    db.recordBigram(prev: p1, input: state.finalizedText, output: text)
    if let p2 = prev2Output {
        db.recordTrigram(prev2: p2, prev1: p1, input: state.finalizedText, output: text)
    }
    if InputHandler.particles.contains(p1),
       let prevContent = mostRecentContentWord() {
        db.recordSkipBigram(prev: prevContent, input: state.finalizedText, output: text)
    }
}
```

**読み出し**：

- `InputHandler+Candidates.swift` の予測候補組み立てで、`bigram` の後ろに `mostRecentContentWord` を prev とした `fetchSkipBigram` 結果を追加（既出を除外）。
- `InputHandler+SuccessorMode.swift` `suggestSuccessors` で、bi-gram + tri-gram + 格助詞 fallback の後ろに skip-bigram top を並べる。

### 副作用

- DB サイズ：助詞確定ごとに skip_bigram 1 行追加。bigram と同等。
- 改善 G（recency）と組み合わせれば古い skip-bigram は自動的に上位から退場する。

### テスト

- `今日`→`を`→`行く`、`今日`→`が`→`走る` を確定 → `fetchSkipBigramTop(prev: "今日")` が `["行く", "走る"]` を返す
- 通常組成中に `今日`→`を` の後 `い` を打つと、bigram (`を → い*`) には無い `行く` が予測候補に出る
- 助詞でない語 (`今日 → 行く`) を直接続けたときは skip-bigram に記録されない（直前が particles でないため）
- `committedHistory` が 5件超でドロップする

## リスク・オープンポイント

- **改善 G の τ 値**：30日は経験則。実運用ログで再調整。
- **改善 G の Swift 6 concurrency**：`var clock` は actor isolation の検討が必要。`@MainActor` の現状を維持できるか、コンストラクタ DI に変えるか。
- **改善 H の committedHistory = 5**：他参照箇所がないため安全。将来 trigram の prev3 等を追加するなら見直し。
- **改善 E のフレーズ学習粒度**：1セグメントのみ Space 確定で `confirmed = seg.selectedText` 1件のときは合成記録をスキップする（`segments.count >= 2` ガード）。
- **誤学習リスク総体**：F で短い prefix が増え、H で skip-bigram が増えるが、G の recency が古い誤学習を退場させるので相殺見込み。実装後 1〜2週間で挙動を観察し、τ 調整の可否を判断する。

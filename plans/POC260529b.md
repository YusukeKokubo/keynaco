# POC260529b: requireJapanesePrediction（組成中の予測補完）の効果検証

status: E2E 検証済み（2026-05-29）/ 判定: **安全に有効化可。コールドスタート補完として価値あり**（履歴の代替ではなく補完）
関連: [IDEA260529](../ideas/IDEA260529.md) #2 / 姉妹 POC [POC260529](POC260529.md)（personalization）

## 仮説

`ConvertRequestOptions.requireJapanesePrediction` を true にすると、組成中に部分読みから
「語の完成形」「活用・助詞付き形」が候補に加わり、打鍵を減らせる。keynaco は現状 false。

## AzooKey の予測機構（コード読解で確定）

`KanaKanjiConverter.swift` を読んだ結果、予測は3系統ある:

| 機構 | API | keynaco での可否 |
|------|-----|-----------------|
| [A] 組成中予測 | `requireJapanesePrediction`（requestCandidates 内、`getPredictionCandidate` で最大3件を mainResults に注入） | ✅ 使える。本 POC の対象 |
| [B] 確定後予測（ゼロヒント後続語） | `requestPostCompositionPredictionCandidates(leftSideCandidate:)`（助詞最大3・絵文字含む） | △ **Successor モード（rejected F-1）と同概念**。UX 不適合で却下済み。ただし F-1 の「データ空問題」は辞書駆動なので解消される |
| [C] 次文字予測 | `predictNextCharacter` | ❌ **zenz-v2 専用**。v3.1 では不可（コード内に明記） |
| 英単語予測 | `requireEnglishPrediction`（NSSpellChecker） | 別軸。今回対象外 |

## 判明したこと・論点

1. **効果は明確**。完成形（ありがとう等）は文句なく有用。活用・助詞付き（確認し等）は好み次第。
2. **keynaco の既存機能と重複・競合の懸念**:
   - history prefix 検索（「よ」→「よろしくお願いします」, rejected D-2 で「カバー済み」とした機構）
   - 1 モーラサジェスト（recent/frequent commits）
   - これらは**個人化**された予測、[A] は**辞書ベース**の汎用予測。補完関係だが、候補リストが混み合う。
3. **パイプライン整合が未確認**: [A] は mainResults 高位に注入される。keynaco の `buildCandidateList`
   優先順位（ひらがな固定 / ユーザー辞書 / Zenzai top1 / 履歴 / 数字日時 / 辞書候補）の
   どこに流れ込むか、固定枠（Zenzai top1・ひらがな）を押しのけないかを E2E で見ないと分からない。
   → CLAUDE.md「組成 state 依存の機能は単体テストだけだとタイミングバグを見逃す」に該当。
4. **レイテンシ未計測**: requireJapanesePrediction は全文 clause 処理＋予測生成で追加コスト。
   concept.md は「名詞・固有名詞のサジェストは最速で」を重視。autoShow ホットパスに載るか要確認。

## 実装コストの確認（2026-05-29 追記）

当初「予測候補（入力より長い完成形）は `requestCandidates` のカバレッジフィルタ
（`composingCountValue == inputLength`, AzooKeyConverter.swift:131）で弾かれるのでは」と懸念したが、
ハーネスで全候補の composingCount を実測した結果 **PASS（弾かれない）**:

- 「ありがとう」の composingCount は **surface長(5) ではなく入力読み長(4)** ＝ inputLength と一致。
  予測の「う」は入力読みに対応づくため count が増えない。`へんかん→変換する`, `かんが→考える` も同様に PASS。
- ※ `ComposingCount` には `.composite(lhs:rhs:)`（文節連結）case があり、keynaco の `countValue` は
  再帰加算で正しく扱っている（ハーネス初版はこの case を落として全部 count=0 と誤判定した。修正済み）。

→ **実装は最小**: `baseOptions` の `requireJapanesePrediction: false → true` の1箇所で予測候補が
`azooKeyCandidates` に流れ込み、`buildCandidateList` に辞書候補として入る。フィルタ改修不要。
（末尾1文字かなの残余フィルタ 143-150 で活用形が削られる懸念 → **2026-05-29 検証済み**:
`kakunin`→space で `確認 / 確認し / 確認さ / 確認の` が全て残存。正常候補と共存して残るので
フォールバックではなくフィルタを正規に通過。完成形 `ありがとう`/`おはよう` もクリーンに通る。）

## 既存機能との関係（「置き換え」可否の論点・2026-05-29）

ユーザー方針は「既存機能は気にせず、より良ければ置き換える」。ただし計測上は**置き換えではなく棲み分け**:

- **1 モーラサジェスト**（1 文字時）: 入力1モーラで発火。辞書予測は2モーラ以上の部分読みでないと
  有用な完成形を出せない（1モーラは曖昧すぎる）。**発火する入力長が違う**。
- **history prefix**: ユーザーの**過去フレーズ**（情報共有・よろしくお願いします）を個人化予測。
  辞書予測は**汎用完成形**（ありがとう・考える）で、個人語彙は出せない。**価値の軸が違う**。

→ 辞書予測は history/1モーラを**代替できない**（個人化を持たない）が、初日から効く汎用補完を**追加**する。
E2E では「追加して候補リストが破綻しないか」「history と二重で混まないか」を見るのが本質。

## E2E 検証結果（2026-05-29・`/keynaco-ime-sandbox`・実機 useRealDB）

ブランチ `poc/require-japanese-prediction`（commit 826e980）で `requireJapanesePrediction: true` にし、
実 DB（ユーザーの実履歴）で候補リストを観察した。

**1. パイプライン整合: 破綻なし ✅**
予測候補は**常に `dictionary` セクション（最後尾）**に入る。固定枠・履歴を一切押しのけない:

| 入力 | 候補（section） | fixedEnd/historyEnd |
|------|----------------|--------------------|
| おは（履歴なし） | **おは\<fixed>** / おはよ\<dict> / おはよう\<dict> | fixed=1 |
| suihuto + "Pythonやの" | **SWIFT\<fixed>** / スイフト\<dict> / すいふと\<dict> | fixed=1（Zenzai promote 維持）|
| jaba + "蛇が庭に" | **蛇腹\<fixed>** / じゃばら\<dict> / 蛇場\<dict> / Java\<dict> | fixed=1 |
| henkan（履歴豊富） | 変換\<hist> / 変換履歴\<hist> / 変換候補\<hist> / 変換し\<dict> / 変換する\<dict> | history=3 |

→ Zenzai top1・ひらがな固定・履歴がすべて予測より上に保たれる（buildCandidatelist の優先順位どおり）。

**2. レイテンシ: 無視できる ✅**
予測 ON/OFF の差分（Zenzai OFF で分離、30回平均）は Δ = -0.08〜+0.22 ms ＝ノイズ範囲。
autoShow ホットパスに載せても体感差なし（concept.md「名詞サジェストは最速で」をクリア）。

**3. 価値: コールドスタート補完（履歴の代替ではなく補完）**
- 履歴なし（`おは→おはよう`）: 予測が**唯一の価値**。初日から効く。
- 履歴豊富（`henkan→変換履歴/変換候補`, `yoro→よろしくお願いします`, `jissou→実装して`）:
  **履歴の方が優秀**。予測（変換ミス・実相寺等）は冗長〜軽ノイズだが履歴の下なので無害。
- → personalization（データが増えるほど良い）と**データ軸が逆**。予測はデータがない時ほど効く。両者は補完的。

**4. ノイズ**: `実相寺`・`喜び`・`おはよ`（未完）等は出るが dict 位置（高位ではない）。許容範囲。

## 判定と次アクション

- **安全に有効化できる**（破綻なし・レイテンシ無視可）。コールドスタート/カバレッジ補完として価値あり。
- 「既存機能の置き換え」にはならない（history-prefix/1モーラは個人化で、データがある時はそちらが上）。
  → 既存機能は削らず**併存**が妥当。予測は穴（履歴のない語）を埋める。
- 残ノイズ（実相寺等）が気になれば将来 dict 位置でのフィルタを検討（優先度低）。
- **採否**: ON のまま main にマージし、`docs/observation.md`（実装済み・価値未確定）で経過観察するのが筋。
  卒業条件＝「履歴のない語の補完で打鍵が減る場面を体感」、廃止条件＝「ノイズが気になる/体感変化なし」。

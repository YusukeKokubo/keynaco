# パフォーマンス改善計画

## 背景

IME はキー入力ごとにメインスレッドで処理を実行する。遅延が体感されると入力ミスや使いにくさに直結するため、ホットパスの I/O・アロケーションを削減する。

---

## P1: SQLite prepared statement キャッシュ（最優先）

### 問題
`DatabaseManager.queryStrings` / `execute` はキー入力のたびに `sqlite3_prepare_v2` → `sqlite3_finalize` を繰り返す。`buildCandidateList` だけで 1 打鍵あたり 6〜8 本、`suggestSuccessors` でさらに 4〜5 本走る。

### 対策
```swift
private var stmtCache: [String: OpaquePointer] = [:]

private func preparedStatement(for sql: String) -> OpaquePointer? {
    if let cached = stmtCache[sql] { return cached }
    var stmt: OpaquePointer?
    guard sqlite3_prepare_v2(db, sql, -1, &stmt, nil) == SQLITE_OK,
          let s = stmt else { return nil }
    stmtCache[sql] = s
    return s
}
// queryStrings / execute 内で preparedStatement を使い、
// 呼び出し後に sqlite3_reset + sqlite3_clear_bindings。
// deinit で stmtCache.values.forEach { sqlite3_finalize($0) }
```

### 期待効果
1 打鍵で 10〜20 回の SQL parse/codegen が消える。

## P2: デバッグ呼び出しが本番ビルドに漏れている（バグ修正）

### 問題
`InputController.swift`（`IMKTextInputAdapter.insertText`）:
```swift
MainActor.assumeIsolated { EventViewerWindow.shared.addCommit(text) }
```
`#if DEBUG` ガードなし。本番ビルドでも全確定ごとに `EventViewerWindow.shared`（NSStatusItem含む）を操作している。`addEvent` 等は `#if DEBUG` 済み。

### 対策
```swift
func insertText(_ text: String) {
    #if DEBUG
    MainActor.assumeIsolated { EventViewerWindow.shared.addCommit(text) }
    #endif
    client?.insertText(text, replacementRange: .notFound)
}
```

## P3: DB 書き込みをバックグラウンド化

### 問題
確定時に走る以下の処理がメインスレッド同期:
- `db.recordPrefixes` — prefix 数本の INSERT を直列実行
- `db.recordBigram` / `recordTrigram` / `recordSkipBigram`
- `azooKeyConverter.commit` — AzooKey 学習データ永続化

長い読みの確定後に次キー入力が詰まる可能性がある。

### 対策
```swift
private let writeQueue = DispatchQueue(label: "keynaco.db.write", qos: .utility)
```
`commitText` 内の record 系 / `azooKeyConverter.commit` を `writeQueue.async { }` に投げる。  
読み取りは依然同期（確定直後に同じ読みを参照することは稀）。

### 注意点
- `DatabaseManager` は `@unchecked Sendable` なので queue 跨ぎはコンパイル通る
- `withTransaction` を使って複数 INSERT を 1 コミットにまとめることで write ロック時間も削減

## P4: history / user_dict の exact + prefix を 1 クエリ化

### 問題
`DatabaseManager.fetchHistoryExact` + `fetchHistoryPrefix` の 2 本が別々に `prepare` / `step` / `finalize` を実行。`buildCandidateList` のホットパス。user_dict も同様。

### 対策
UNION ALL + マーカカラムで 1 本化:
```sql
SELECT output, 0 AS kind FROM history
WHERE input = ? COLLATE NOCASE
UNION ALL
SELECT output, 1 FROM history
WHERE input LIKE ? AND input != ?
GROUP BY output
ORDER BY kind, (count * 1.0 / (1.0 + (? - used_at) / ?)) DESC
LIMIT 20
```
返値は kind で 2 つに分割してそれぞれ利用。prepare 回数が半減。

## P5: fetchBigramTopCount を fetchBigramTop と統合

### 問題
`InputHandler+SuccessorMode.swift:18-42` で `fetchBigramTop` 直後に `fetchBigramTopCount` を別クエリで呼んでいる。

### 対策
`fetchBigramTop` の返値に最大 count を付与する API に変更:
```swift
func fetchBigramTop(prev: String, limit: Int = 20) -> (outputs: [String], maxCount: Int)
```
または内部で `MAX(count)` を同じ SELECT に含める。呼び出し元は同一 prepare の結果から両方取得。

## P7: candidates.removeAll の O(n) スキャン削減

### 問題
`buildCandidateList`（`InputHandler+Candidates.swift:238-244`）でカタカナ・ひらがな挿入前に `removeAll { $0 == x }` を実行している。同じ要素は `insertedSet` で管理されているので、先に Set チェックすれば走査不要。

### 対策
```swift
if !katakanaInHistory {
    // candidates 内の既存エントリは insertedSet で管理済み
    // removeAll 不要: candidates.insert で先頭に差し込む前に contains を確認するだけ
    if insertedSet.insert(katakana).inserted {
        candidates.insert(katakana, at: 0)
        fixedCount += 1
    }
}
```

# IDEA260327: 学習強化 第三弾以降の発展アイデア集

PLAN260429b（第一弾: Successor チェーン解禁・recordPrefixes 5+）と
PLAN260501（第二弾: フレーズ単位学習・閾値 3+・recency・skip-bigram）が完了した時点での、

## カテゴリ A: 学習信号の質を上げる（既存 N-gram 基盤の改良）

### A-1. 文脈リセット（句読点・Enter での n-gram chain 切断） ★★★

**現状の問題**
`commitText` は文末「。」確定後も `lastCommittedOutput = "。"` `prev2Output` を保持し続ける。
次の文の先頭語に対して `(。, 次文先頭)` の bigram が学習され、文を跨いだ意味の薄い連想が n-gram テーブルを汚す。

**設計**
- `InputHandler.particles` と並列に `sentenceTerminators = ["。", "！", "？", "\n"]` を定義
- `pushCommitted(text)` 内で `sentenceTerminators.contains(text)` のとき `committedHistory.removeAll()`
- skip-bigram の `mostRecentContentWord()` も同様に文をまたがない

**副作用**
- 既存テストで「。」の後の bigram が消える可能性。テスト調整必要。

**期待効果**
- 誤候補比率の低下。tri-gram の精度向上（文末記号が prev2 になるノイズが消える）。

**規模**: 1〜2 時間。1 ファイル数行 + テスト数本。

---

### A-2. 候補スキップの負シグナル ★★

**現状の問題**
auto-show で候補に出ていたのに別の語を選んだエントリは、count++ 機会を逃すだけ。
古い高頻度誤学習（例: 「とう」→「投資」）が新しい正解（「東京」）に追いつかれるまで時間がかかる。

**設計**
- `commitText` 時に「直前の表示候補リストのうち選ばれなかったもの」を引数で受け取る
  - 候補リストは `CandidateContext` に存在するが、選ばれなかった候補は呼び出し側で diff 必要
- `db.markSkipped([reading: ..., output: ...])` を新設し、`used_at = used_at` のまま `score *= 0.95` 相当の効果を出す
  - 物理的には新カラム `skip_count` を追加、score 計算式を `count / (1 + age/τ) / (1 + skip_count * 0.05)` に拡張

**副作用**
- score 計算が複雑化。recency と相互作用するので調整が難しい。
- skip 多発で score が異常に下がるリスク → cap が必要。

**規模**: 1 日。score 式の調整に時間がかかる。

---

### A-3. 訂正シグナル（直前確定の Undo + 別語確定）★

**現状の問題**
ユーザーが間違えて確定 → Backspace で消す → 別の語を選び直す、という最も信頼度の高い「正解信号」が学習に使われていない。

**設計**
- `InputHandler` に `lastCommit: (reading: String, output: String, at: Date)?` を保持
- 直前 commit の文字列がすべて Backspace で消され、同じ reading で別 output が確定したら：
  - 元 output に大ペナルティ（`count *= 0.5` or 削除）
  - 新 output に大ボーナス（`count += 5`）

**副作用**
- 「単に消して別の文を打ち始めた」ケースとの誤検出。reading の一致条件で絞れば回避可能。
- 確定後の編集（数文字消して別の続きを打つ）は対象外にする必要あり。

**期待効果**
- 誤学習の自動修正。明示的な訂正で1回分の意思を10倍重く扱える。

**規模**: 半日〜1日。検出ロジックがやや繊細。

## カテゴリ B: 入力モダリティを増やす（タイプ数を直接削る）

### B-1. Tab で唯一の高信頼候補を即確定 ★★★

**設計**
- 組成中、`fetchHistoryExact(reading)` が 1 件 & その score が閾値 N 以上のとき：
  - Tab で Space + Enter 相当（即 commit）
- 候補ウィンドウ表示の有無に関わらず動作（Tab は組成中の隠し近道）

**副作用**
- 既存の Tab 動作（候補選択中の次候補移動、セグメントモードの境界調整）と衝突しない箇所のみ。
  組成中 & 候補未選択 & 唯一高信頼 のときに限定。

**期待効果**
- `おつ` Tab で `お疲れ様です` 一撃。Space + Enter の 2 打が 1 打に。

**規模**: 数時間。

---

### B-2. 子音のみ入力（ATOK 風）★★

**設計**
- `RomajiConverter` に `hiraganaToConsonants(_ hiragana: String) -> String` を追加
  - `おはよう` → `ohyu`（行頭母音は残す + 子音抽出）
  - 別ルール：`a/i/u/e/o` を全削除すると `おはよう → hy`、これは過剰圧縮
  - 妥協案：母音 a/i/u/e/o のうち子音直後のもののみ削除（`oh-y-u` → `ohyu`）
- `recordPrefixes` 時に並行して consonant index に `(consonants, output)` を記録
- 別テーブル `consonant_index`：
  ```sql
  CREATE TABLE consonant_index (
      consonants TEXT NOT NULL,
      output     TEXT NOT NULL,
      count      INTEGER DEFAULT 1,
      used_at    INTEGER NOT NULL,
      UNIQUE(consonants, output)
  );
  ```
- ASCII pendingRomaji 段階（母音待ちの状態）でも `consonant_index` を引いて先取り候補表示

**副作用**
- 誤発火が増える。1〜3 文字の子音マッチは候補が爆発する → 閾値 4 文字以上 + score 高優先のみに制限。
- ASCII モードと混乱しないよう日本語モード組成中限定。

**期待効果**
- 長語ほど劇的。`okstdss` で `お先に失礼します` のような圧縮率（条件次第）。

**規模**: 2〜3 日。consonant 抽出ルールの設計と誤発火対策がメイン。

---

### B-3. ユーザー定義 snippet（短縮入力マクロ）★★★

**設計**
- 設定画面（`Sources/Settings/`）に「Snippets」タブ追加
- スキーマ：
  ```sql
  CREATE TABLE snippets (
      trigger TEXT PRIMARY KEY,  -- 例: ";mail"
      output  TEXT NOT NULL,     -- 例: "yusuke.kokubo@leaner.co.jp"
      enabled INTEGER DEFAULT 1
  );
  ```
- `InputHandler` で組成中に `;<word>` パターンを検出 → snippets テーブル exact match → 即 commit
- ASCII モード中も発火させるかは要検討（メール文中で打つので発火させるべき）

**副作用**
- `;` がトリガとして奪われる。escape 用に `\;` を許す or プレフィックス文字を設定可能に。

**期待効果**
- メール・slack・コミットメッセージで桁違いに打鍵削減。学習ではないが日常の確定的展開。

**規模**: 1〜2 日（テーブル + 設定画面 + 入力処理）。

---

### B-4. クリップボード語の即時候補化 ★

**設計**
- `NSPasteboard.general` を `InputController` で監視（または都度 fetch）
- 直近コピー文字列が ASCII or 既存変換結果に該当する場合、組成中の候補先頭近くに差し込む
- 読み推定：
  - クリップボード内容がカナ → そのまま reading として一致
  - 漢字混じり → 既存 history で逆引き、見つからなければ candidate として扱わない
  - ASCII 識別子 → 別途 `;c` や `;v` のショートカットで貼り付け候補化

**副作用**
- プライバシー懸念（クリップボードを常時読む）。サンプリング間隔を絞るか、組成開始時のみ読む。

**期待効果**
- リファクタで変数名を変えた直後の入力で激強。

**規模**: 1 日。

---

### B-5. 「最後の確定」再挿入キー ★

**設計**
- `lastCommit` を保持済み（A-3 で追加予定）
- 組成空状態で特定キー（例: F11 or ⌃; ）で `lastCommit.output` を再挿入

**副作用**
- ほぼなし。トリガキーの選定のみ。

**期待効果**
- 同じ語を続けて打つ場面で 1 打。学習量に依存しない。

**規模**: 数時間。

## カテゴリ C: 文脈スコープ（誤学習を「文脈外」に追い出す）

### C-1. アプリ別プロファイル ★

**設計**
- `InputController` が IMK の `client()` から `bundleIdentifier()` を取得し `InputHandler` に渡す
- `DatabaseManager` の各 fetch を `score *= (app == currentApp ? 1.0 : 0.7)` で補正
- テーブル分割ではなく score 重み付けにすることで実装軽量化
- 全アプリで使う固定候補（カタカナ等）は影響を受けない

**副作用**
- bundleID の取得失敗時は重み 1.0（全テーブル横断）にフォールバック。
- 学習データに `app_id` カラムを追加すると過去データの扱いが面倒 → 「最後に確定したアプリ」だけ保持して相対距離で重みづける形でも可。

**期待効果**
- Slack の口語と Xcode の識別子が混ざらない。

**規模**: 2〜3 日（スキーマ移行 or 軽量重み付け）。

---

### C-2. AzooKey N-best のユーザー学習リランキング ★★

**設計**
- 現状 `AzooKeyConverter.convert(reading)` は単一候補 or 順序固定で返している（要確認）
- N-best を取得し、各候補に対して `db.fetchHistoryExact(reading)` の score を加算してリランキング
- 結果は AzooKey セクションの内部並びに反映

**副作用**
- AzooKey 自体の学習機能（`azooKeyConverter.commit` で動いているはず）と二重学習にならないよう要確認。

**期待効果**
- 履歴に無い候補でも、AzooKey の N-best から選ぶ際にユーザー傾向が反映される。
- Successor / 予測候補の精度向上にも波及。

**規模**: 1〜2 日。AzooKey の N-best API 確認が前提。

---

### C-3. 軽量ローカル LM での再ランキング（フロンティア） ☆

**設計**
- AzooKey 内蔵の確率モデル + ユーザー学習を Bayesian 合成
- または小型の Transformer LM を CoreML で動かして trigram の代替に
- 推論コストとレイテンシのトレードオフ評価が必須

**副作用**
- 実装コストが大きい。常時メモリ使用量増。
- IME はレイテンシ要件が極めて厳しい（数 ms）ため、推論時間を切り詰める必要あり。

**期待効果**
- 文脈理解が n-gram の限界を超える。長距離依存・意味的類似性。

**規模**: 2〜4 週間（プロトタイプ含む）。

## カテゴリ D: 再ランキング・正規化

### D-1. 同じ output が複数 reading で学習されているときの統合 ★

**設計**
- `(reading, output)` で UNIQUE だが、`(reading_a, output_X)` `(reading_b, output_X)` のように同 output 異 reading で別行になっている
- 候補表示時に同 output の score を合算してから並べ替えると、頻出 output が上位に来やすい
- 既に `fetchBigramTop` は `SUM(count)` を使っており、history にも適用するイメージ

**副作用**
- prefix 学習で同 output が複数行に分散している前提と整合する。

**期待効果**
- `おはよう` 関連の prefix 群が分散していても合算で上位に。

**規模**: 数時間。

---

### D-2. 短い reading の score 上限 ★

**設計**
- 1〜2 文字 reading は誤学習が支配的になりやすい
- score に reading 長による下駄（`* min(1.0, len(reading) / 3)`）を掛けて短 reading の影響を抑える
- 長い reading で確定された prefix エントリは「実は長い phrase の一部」として推測できるので影響は限定的

**期待効果**
- 改善 F（閾値 3 化）の副作用緩和。

**規模**: 数時間。

## 個人的な推し（再掲）

**A-1（文脈リセット）が最強の費用対効果**。1〜2 時間で入って n-gram の精度が定量に向上する。
PLAN260501 で導入した skip-bigram の質も上がる（文をまたいだ skip がノイズになるのを防げる）。

**B-1（Tab 即確定）と B-3（snippet）** は学習基盤と独立して効くので、いつでも入れられる。
特に B-3 は「学習に依存せず即タイプ削減」できる唯一のカテゴリで、第二弾までの学習パイプラインとは別軸の価値。

**B-2（子音のみ入力）** はロマン枠だが、PLAN260501-E（フレーズ単位学習）と組み合わせると
`お疲れ様です` → `oktrsmds` のような 8 打圧縮も視野に入る。実装コストは大きいが、
完成すれば他 IME に対する差別化要因になり得る。

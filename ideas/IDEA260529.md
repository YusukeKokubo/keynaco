# Zenzai/AzooKey の未使用ポテンシャルを引き出す

## 背景

keynaco は AzooKey API + Zenzai（zenz-v3.1-small）を変換エンジンに使っているが、
「ポテンシャルを十分引き出せているか」を棚卸ししたところ、コアの条件付き変換
（`leftSideContext` による同音異義語 disambiguation）は的確に使えている一方で、
Zenzai/AzooKey 固有の尖った機能のいくつかが未使用のまま放置されていることが分かった。

このメモは未使用レバーを「効果見込み順」に記録し、忘れられないようにするもの。

**進捗（2026-05-29）**: #1 personalizationMode は POC 実施済み（データ量律速でデータ待ち保留）。
#2 predictive completion は E2E 検証して有効化・main マージ済み。残り未着手は #3・#4・#5。
次に着手するのは **#4 inferenceLimit チューニング**（計測ハーネスが手元にあり最も安い）。

### 引き出せている部分（参考）

- Zenzai ON + `leftSideContext`：IMK `selectedRange()` 前文（最大300字）＋ `sessionTextBuffer`
  を毎キー渡す（`InputController+LLM.swift:8-32`）。POC260524 で文脈バイアスの効果は実証済み。
- 確定時の学習フック `updateLearningData` / `commitUpdateLearningData`（`AzooKeyConverter.swift:161-173`）。
- `requestRichCandidates` を Space 押下時のみ true（autoShow のレイテンシと N-best の豊かさをトレード）。

### 試して棄却済み（蒸し返し不要）

- `topic` / `style` / `preference` 制御トークン：zenz-v3.1-small では測定可能な効果なし
  （`docs/rejected.md` G-1 / `plans/POC260524.md`）。
- `needTypoCorrection`：iOS フリック向けでローマ字直接入力では恩恵薄（`docs/rejected.md` E-2）。

## 未使用レバー一覧（効果見込み順）

### #1 personalizationMode が常に nil 【✅ POC 済み → データ待ち保留（[POC260529](../plans/POC260529.md)）】

> 結果: 機構は有効（`めいし→名詞`）だが、学習元の `daily_log` が2日分2470字と少なく過学習で破綻。
> `daily_log` が数万字に育った時点で α=0.3〜0.5 で再計測する。leftSideContext とは直交（topic と違い冗長でない）。

`AzooKeyConverter.swift:103-119` の `ZenzaiMode.on(..., personalizationMode: nil, ...)`。
zenz-v3 のパーソナライゼーション（ユーザーの過去テキストに変換分布を恒常的に寄せる機能）を
完全に無効化している。`leftSideContext`（直近の文脈）とは別軸の「その人の語彙・言い回しへの
持続的適応」であり、keynaco は SQLite に確定履歴を大量に持っているので入力ソースの相性が良い。

- 検証方法：`/keynaco-ime-sandbox` で、履歴由来の base text を与えた場合と nil の場合で
  同じ読みの候補順がどう変わるかを A/B 測定（POC260524 で leftSideContext を測ったのと同じ筋）。
- リスク：既存の history スコア式ランキングと二重バイアスになる可能性。効果の切り分けが要。

### #2 predictive completion が死んだコードパス 【✅ 有効化・main マージ済み（[POC260529b](../plans/POC260529b.md)）】

> 結果: `requireJapanesePrediction: true` で完成形・活用形（ありがと→ありがとう 等）を追加。
> 予測候補は dictionary セクション（固定枠・履歴の下）に入り順序を壊さず、レイテンシも無視可。
> コールドスタート補完（履歴のない語の穴埋め）として有効。observation.md で経過観察中。

`uniquePredictions` は `[]` 固定、`requireJapanesePrediction` も false
（`InputHandler+Candidates.swift:81-82`）。AzooKey の予測変換（途中まで打って続きを予測）を
一切使っていない。observation.md の「1モーラサジェスト」を自前の履歴 warmload で実装しているが、
これは AzooKey の予測 API と機能が重複している。エンジン側の予測力で置き換え・強化できる可能性。

- 検証方法：`requireJapanesePrediction = true` にして predictive 候補を取得し、
  自前 1モーラサジェスト（recentCommits / frequentCommits）と質を比較。
- 注意：自前実装には「直近セッション優先」という意図があるので、単純置換ではなく統合設計が要。

### #3 live conversion（ライブ変換）未実装

打鍵ごとに確定済みテキストへ反映していく方式。Zenzai のリランキング力が最も体感に出る機能で、
プロダクトの見せ場になり得る。ただし候補ウィンドウ中心の現 UX と設計思想がぶつかる。

- 採用は要判断。`docs/concept.md` のポジショニングに合致するか先に確認すること。

### #4 モデルサイズ / inferenceLimit のチューニング 【両方✅検証済→ともに非レバー（[POC260529c](../plans/POC260529c.md)）】

> **inferenceLimit**: cap は難・同音異義でのみ効き、全ケース limit≤3 で収束。デフォルト 5 は収束点に
> 余裕を持って上回り、5 超はゼロ改善・レイテンシ増の純損、3 未満は品質劣化リスク。**5 が適切で変更不要**。
>
> **モデルサイズ（2026-05-29 調査）**: Miwa-Keita/HF のラインナップは v3.1-xsmall(22.5M) / v3.1-small(90.5M) /
> v3.2-small(95.1M)。**v3 世代に medium/large は存在しない**＝small が事実上の上限。より大きいのは v2.5-medium だが
> v3 の条件付き変換（leftSideContext = keynaco の killer feature, POC260524）を失うので不可。xsmall への縮小は
> 品質を落とすだけで動機薄（現レイテンシ ~12-67ms は許容内）。→ **サイズ軸では small がベスト。**
>
> 唯一の更新候補は v3.1-small → **v3.2-small**（同サイズ・右文脈 `` 対応）だが、**AzooKey 0.11.2 の API は
> v3.2 右文脈を扱えない**（`ZenzaiVersionDependentMode` は `.v3` のみ・右文脈フィールドなし）。活かすには
> AzooKey アップグレード＋右文脈の配線が前提。ドロップイン（新重みのみ）実測の結果は POC260529c 参照。

### #5 textReplacer / specialCandidateProviders 未使用（優先度低）

`textReplacer: .empty` / `specialCandidateProviders: nil`（`AzooKeyConverter.swift:89-100`）。
AzooKey の拡張ポイント。ユーザー辞書を別経路で処理しているため当面は不要だが、
将来「ユーザー定義の置換ルール」を入れるなら textReplacer が正規の入口。

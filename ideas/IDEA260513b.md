# セグメント境界を LLM で同期的に決定する

## 背景

現在のセグメントモード（Space 押下時）のフローは以下の2ステップになっている。

1. `enterSegmentMode()` が即座に AzooKey の `segmentize` 結果を表示（速いが精度が低い場合がある）
2. `LLMSegmentConverter` が非同期で走り、結果が来たら `applyLLMSegmentResult()` で上書き

このため「悪い分割が一瞬表示されてから正しい分割に切り替わる」ガタつきが生じる。
今日修正した「せっ＋ていがめんの」や将来的な類似パターンに対してもヒューリスティックを積み上げ続ける構造になっている。

## 前提

- keynaco は macOS 26 以降を対象とし、Apple Intelligence（`FoundationModels`）が常に利用可能
- `SystemLanguageModel.default.availability` のフォールバック分岐は不要

## 提案

`enterSegmentMode()` の中で LLM を**同期的**に呼び出し、結果が揃ってから `SegmentState` を構築して返す。

### なぜ「同期」でよいか

- `handle(event:client:)` がブロックしても、OS がキーイベントをバッファリングするためユーザーの入力は欠落しない
- 100〜300ms 程度の待機であれば体感上は「変換に少し時間がかかる」で済む
- 2ステップの表示切り替えが消えるため UX が安定する

### タイムアウト戦略

LLM が想定より遅い場合（または推論キューが詰まっている場合）はタイムアウトで打ち切り、今の AzooKey 分割に降りる。

```
Space 押下
  └─ enterSegmentMode()
       ├─ AzooKey.segmentize()  ← 高速（常に実行）
       ├─ LLM.inferBoundaries() ← 同期待ち（上限 300ms 程度）
       │    ├─ OK  → LLM 境界で SegmentState 構築
       │    └─ timeout → AzooKey 境界で SegmentState 構築（現行と同じ）
       └─ return CandidateAction
```

### 実装イメージ

```swift
// enterSegmentMode() 内
let llmResult = LLMSegmentConverter.inferSynchronously(
    hiragana: fullReading,
    azooKey: azooKeyConverter,
    leftSideContext: azooKeyLeftContext,
    timeoutMs: 300
)
if let pairs = llmResult {
    applyLLMBoundaries(pairs: pairs, llmWholeText: pairs.map(\.token).joined())
} else {
    // 既存の AzooKey segmentize パス
}
```

`inferSynchronously` の内部は `DispatchSemaphore` で FoundationModels の async API を同期待ちする。

## 削減できるもの

この変更が成立すれば以下が不要になる（またはシンプル化できる）。

| 削除・簡略化対象 | 理由 |
|----------------|------|
| `applyLLMSegmentResult()` | 非同期上書きパスが不要 |
| `segmentLLMTrigger` プロパティ | LLM は enterSegmentMode 内で完結 |
| `InputController` の `applyLLMScheduling()` 呼び出し（セグメント分） | 同上 |
| `tryManualBisection()` の促音ヒューリスティック | LLM が正しく境界を推論できれば不要になる可能性 |

`LLMSuccessorFetcher`（Successor モード）は非同期のままで構わない。

## 懸念点・検討事項

- **遅延の実測**: Apple Intelligence の on-device LLM がどの程度の速度で返るか、実機で計測してから timeout 値を決める
- **Swift 6 Sendable**: `DispatchSemaphore` を使った async→sync ブリッジは Swift 6 の strict concurrency でワーニングが出る可能性がある。`withCheckedContinuation` + `DispatchQueue.async` パターンの方が安全
- **InputHandler が struct**: `enterSegmentMode()` は `mutating func` なので、呼び出し側（`InputController`）でアクター境界をどう扱うか要確認

## 優先度・難易度

| 項目 | 評価 |
|------|------|
| 期待効果 | 高（ガタつきゼロ・ヒューリスティック削減） |
| 難易度 | 中（async→sync ブリッジと timeout 設計が主な工数） |
| リスク | 低（timeout fallback で現行動作を保証できる） |
| 着手タイミング | LLM 遅延の実測後 |

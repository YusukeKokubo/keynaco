# Successor 候補を形態素境界で prefix 分割する

## 背景

Successor モードのサジェストは「1 文字列 = 1 候補単位」で扱われる。LLM (`LLMSuccessorFetcher`) のプロンプトは「1語ずつ・助詞は含めない」と指示しているだけで、長さや文節数の制約はない（`splitAndFilterLines` は空行・記号・数字のみを弾く程度）。このため:

- LLM が `"会議に出席する"` のような句を返すとそのまま 1 候補になる
- N-gram でも、ユーザーが AzooKey から「予定です」のような複合表層を一括確定すると 1 bi-gram として育ち、以後 prev → "予定です" として何度も提示される

ユーザーの実体感としては「名詞だけ欲しいのに述語まで採用してしまう」「名詞＋述語の塊から名詞だけ抜く手段がない」という不満につながる。

## 提案

LLM が返した（あるいは N-gram から取得した）長い表層形を、azooKey の形態素境界で**先頭から段階的に切った prefix 候補**として並べる。

```
LLM 出力: "会議に出席する"
  ↓ azooKey で形態素分解
分解結果: [会議 / に / 出席する]
  ↓ prefix 列生成（助詞単独は不採用）
候補列: ["会議", "会議に出席する"]   ← 2文節目以降に体言があれば "会議に出席" も追加
```

## 設計の方向性

1. **対象**: Successor の `pendingSuccessorCandidates` + `successorLLMSurfaceExtras` の中で**2 文節以上**を含むものだけ
2. **分割エンジン**: `AzooKeyConverter` の `segmentize` を再利用（既にセグメントモードで使用済み）
3. **prefix 生成ルール**:
   - 1 文節目までの prefix は基本採用（ただし助詞単独は除外）
   - 2 文節目以降の prefix は「体言で終わる」もののみ採用（述語末尾は元の全体候補と被るのでスキップ）
   - 元の全体候補も最後尾に残す（「述語まで全部欲しい」ケースを潰さない）
4. **重複処理**: 既に同じ表層が `filtered` に居れば追加しない（`mergePendingSuccessorMatches` の seen 集合と同じ仕組み）
5. **件数上限**: `successorMaxCandidates = 5` 内に収める。prefix で枠を食い潰さないよう「同一の親フレーズから生成する prefix は最大 2 つまで」

## 影響範囲

- `Core/Sources/Core/InputHandler+SuccessorMode.swift` の `handleSuccessorMode` 内 `.default` ケース（1打目フィルタリング後）に prefix 展開ステップを挿入
- 形態素分解には `AzooKeyConverting`（既存 DI）を利用。読み情報は不要、表層分解のみ
- N-gram 由来候補にも同じロジックを適用すれば、過去に学習してしまった「予定です」のような複合 bi-gram も自然に救済できる

## 懸念点

- **分解レイテンシ**: azooKey の `segmentize` を 5 候補に対して都度回すコスト。1打目で初めて発火する経路なので体感への影響は限定的だが、結果をキャッシュした方が安全
- **読みフィルタとの整合**: 1打目（ローマ字1文字）で `romajiToInitialKana` を見て読み先頭一致を判定している。prefix で先頭文節を切り出した結果が同じ読み先頭を持つかは「親が一致していれば prefix も一致する」ので安全
- **学習側はどうする?**: ユーザーが prefix 版（"会議"）を採用したとき、`confirmSuccessor` で記録する bi-gram は親（"会議に出席する"）ではなく "会議" 単体になる。これは望ましい挙動（次回からは "会議" が単独で出やすくなる）

## 優先度・難易度

| 項目 | 評価 |
|------|------|
| 期待効果 | 高（毎日の体感に直結。"名詞だけ欲しい"フラストレーションが消える） |
| 難易度 | 中（azooKey segmentize の再利用で済むが、件数上限の配分設計が必要） |
| リスク | 低（既存候補の後ろに足す形なので退行リスク小） |
| 着手タイミング | 即着手可（PLAN260520b として詳細化） |

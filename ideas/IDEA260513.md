# N-gram / History データ品質改善

## 背景

実データ（`history.db`）を分析したところ、学習データの質に影響する複数の構造的問題が見つかった。
2904件の history、2309件の bigram（うち preset 300件）、1507件の trigram が蓄積済み。

---

## 観察された問題

### 1. 助詞・ひらがなのまま確定した語が history 上位を占拠

```
を → を (202回)   は → は (95回)   の → の (86回)
が → が (78回)    に → に (74回)
```

`input == output` かつ全ひらがな助詞の変換は学習価値がなく、有用なエントリのスコアを相対的に下げる。

### 2. prefix 蓄積で count が分散する

1回の確定（例: "じっそう" → "実装"）で prefix 長ぶんのエントリが全部インクリメントされる。

```
じっ    → 実装 (30回)
じっそ  → 実装 (29回)
じっそう → 実装 (33回)
```

exact マッチと prefix マッチのランク差がほぼなくなり、スコアの信号が薄い。

### 3. テストデータが N-gram 上位を独占

「今日は東京は雨です」系列が bigram/trigram の top を占有しており、Successor モードがこのコンテキストに引きずられやすい。

```
東京 | は → は (34回)
雨 | です → です (24回)
今日は | しばらく → しばらく (14回)
```

実際の業務パターン（実装・確認・IME）は count 5〜11 程度で埋もれている。

### 4. Preset bigram が少なく汎用的すぎる

300件、`は → これ/それ/あれ/私/君/彼/彼女/誰/何` 系の汎用パターンのみ。
Successor モードの即時表示閾値（`successorImmediateThreshold = 5`）に合わせて count=5 で seed される設計は適切だが、件数が少なすぎる。

### 5. Skip-bigram がほぼ機能していない

291件、最大 count=4。候補組み立てへの寄与が測定されていない。

### 6. Boundary pref がほぼ未蓄積

1件のみ（`きょうのはうす → きょうの,はうす`）。

---

## 改善アイデア

### A. 助詞・ひらがな単打を history から除外（優先度：高 / 難易度：低）

**変更箇所**: `DatabaseManager+History.swift` の history 書き込み処理

条件: `input == output` かつ（全ひらがな2文字以下、または `["は","を","が","に","の","で","と","も","や","か","へ","より","から","まで","だけ","しか"]` に含まれる）場合は書き込みをスキップ。

あるいは書き込みはするが、候補組み立て時に `is_particle` フラグで最後尾に回す設計でもよい。

**期待効果**: 有用なエントリが上位に浮上し、Successor モードの初回精度が上がる。

---

### B. Preset bigram を拡充する（優先度：高 / 難易度：中）

**変更箇所**: `scripts/generate_preset_bigram_csv.py` と `keynaco/PresetBigram/preset_bigram.csv`

追加候補カテゴリと例:

| カテゴリ | prev | input | output |
|---------|------|-------|--------|
| 業務文書の述語パターン | ご確認 | ください | ください |
| | よろしく | おねがいします | お願いします |
| | ご連絡 | ください | ください |
| 技術語彙（開発者向け） | 実装 | しました | しました |
| | 修正 | しました | しました |
| | 確認 | しました | しました |
| | 実装 | します | します |
| 接続パターン | と | おもいます | 思います |
| | と | かんがえます | 考えます |
| | ことが | できます | できます |
| 時間表現 | 今日 | の | の |
| | 明日 | の | の |
| | 今週 | の | の |

count=5 で seed する現設計を維持し、300 → 1000〜2000件に増やすだけで Successor モードの初回精度を大幅改善できる。

---

### C. Prefix count 設計の見直し（優先度：中 / 難易度：高）

**現状**: prefix 長ぶん全エントリをインクリメント → exact と prefix のスコアがほぼ同値になる

**案1（軽量）**: prefix エントリは count を `+0.5` 刻みにする（or `+1` を exact のみにして prefix は `used_at` 更新のみ）

**案2（抜本）**: history には full reading のみ書き込み、prefix マッチは SQL の `LIKE` クエリのみで処理する。現在も `input LIKE ?` クエリが存在するので互換性は高い。推定でテーブルサイズを 30〜40% 削減可能。

---

### D. テストデータ汚染の緩和（優先度：中 / 難易度：低）

**案1**: Debug ビルドは別 DB パス（例: `history_debug.db`）を使う。Release ビルドの学習データを汚染しない。

**案2**: 同一セッション内（例: 1時間以内）での同一トリプレット `(prev, input, output)` の count 増分を +1/時間 に制限する。繰り返しテストによるカウント爆発を防ぐ。

---

### E. Skip-bigram の有効性検証（優先度：低 / 難易度：低）

候補組み立て時に「skip-bigram が final list に追加した件数」をカウントするデバッグログを追加し、寄与率を測定する。寄与率が < 5% なら一時無効化してクエリコストを削減し、データが溜まった段階で再評価する。

---

### F. Boundary pref の活性化（優先度：低 / 難易度：中）

- 境界修正後に「この読みの分割を覚えました」のフィードバック表示を追加（発見性の向上）
- `boundary_pref` は decay 対象外にする（segmentation 好みは長期的に安定するため）
- よく分割を誤るパターンをプリセット seed する（例: 複合名詞の境界）

---

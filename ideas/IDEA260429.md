## カテゴリ E: UX ― 確定後の訂正フロー

### E-1. Backspace 再変換（undo conversion）★★★

**現状の問題**
確定直後に Backspace を押すと `penalizeHistory` でスコアを下げるだけで、テキストは消えない。
正しく言うと「間違えて確定した語を消して打ち直す」しか手段がなく、打ち直しのローマ字から再度 Space で変換し直す必要がある。多くの IME（Google IME・ATOK）が持つ最重要機能の一つが欠けている。

**設計**
- `InputHandler` に `lastCommittedText: String?`（確定出力そのもの）を保持
  - 現在の `lastConfirmedPair` は `(reading, output)` のタプルなので転用可能
- 組成が空の状態で Backspace を受けたとき `lastCommittedText` が非 nil なら：
  1. `client.insertText("")`（直前確定テキストの削除は IMK 経由では難しいのでアプリ側に `setMarkedText` で代用を検討）
  2. `state.composedHiragana = lastConfirmedPair!.input`（読みを復元）
  3. `enterSegmentMode()` を呼んで即座にセグメント変換モードへ
  4. `lastCommittedText = nil`（1回のみ有効）
- `lastCommittedText` はキー入力のたびにクリア（連続した Backspace には反応しない）

**実装メモ**
- macOS の IMK では直前の `insertText` を取り消す API がない（`NSTextView` の `undoManager` に届かない）ため、
  再変換開始時にアプリ側のテキストを削除する手段として `setMarkedText` の前に
  「deleteBackward:」相当を送る方法（`NSTextView` への直接呼び出し）が使えるか要調査。
  最悪、ユーザーが先に Delete キーで消してから再変換する 2 ステップフローにとどめることも選択肢。
- IDEA260327 A-3「訂正シグナル」と組み合わせると「元 output にペナルティ＋新 output にボーナス」も同時に得られる。

**期待効果**
「確定してしまった」ストレスを大幅削減。誤変換訂正の手順が 1 アクションに。

**規模**: 半日〜1 日（IMK の制約調査込み）。

## カテゴリ F: 変換精度 ― 辞書と候補順

### F-1. ユーザー辞書（固有名詞登録）★★★

**現状の問題**
AzooKey は固有名詞（社名・製品名・人名）に弱く、履歴学習でカバーするしかない。
初回変換では必ずサジェストが外れ、手動で打ち直す必要がある。

**設計**
- DB に `user_dict` テーブルを追加：
  ```sql
  CREATE TABLE user_dict (
      reading TEXT NOT NULL,
      output  TEXT NOT NULL,
      PRIMARY KEY (reading, output)
  );
  ```
- `buildCandidateList` / `buildSegmentCandidates` で `fetchHistoryExact` の直後に
  `db.fetchUserDict(reading: input)` を呼び、履歴と同じ `fixedCount` 枠または直前に挿入
- `Settings/` に「ユーザー辞書」タブを追加（NSTableView で reading/output のペアを管理）
- IDEA260327 B-3（snippet）は「;mail → メールアドレス」のようなマクロ展開だが、
  本機能は「とうきょうと → 東京都庁」のような通常の読み→漢字変換候補の補完。両者は独立して有用。

**規模**: 1.5〜2 日（テーブル + CRUD + 設定画面）。

### F-2. セグメントモードでの bigram 活用 ★★

**現状の問題**
`buildSegmentCandidates(reading:dictCandidates:)` は `fetchHistoryExact` しか見ない。
セグメントを左右に移動しながら候補を選ぶとき、前のセグメントの確定語から bigram を引けば
文脈的に自然な候補を先頭に並べられる。

**設計**
- `handleSegmentModeKey` の左右矢印で文節移動するときに前セグメントの `selectedText` を記憶
- `makeCandidateActionForFocusedSegment` を `prevSegmentText: String?` を受け取る形に変更し、
  bigram 上位と `candidates` を `fetchBigramInList(prev: prevText, list: candidates)` で並べ替え
- 例：「東京（に|で|の…）」のうち bigram で `東京 → に` が学習済みなら「に」が先頭に昇格

**規模**: 数時間。

---

### F-3. `isNounLike` の拡張（動詞・形容詞語尾への格助詞 fallback）★

**現状の問題**
`isNounLike`（漢字/カタカナ末尾のみ）が false なら格助詞 fallback が一切出ない。
「〜します」「〜です」「〜ました」のような文末語の後続（「が」「ね」「よ」「か」「ので」等）は
bigram 未学習の初期状態で Successor モードに入らない。

**設計**
- `isVerbEnding(_ text: String) -> Bool` を追加
  - 末尾が「す」「る」「た」「い」（+ 直前が平仮名）のとき true
- `suggestSuccessors` で `isNounLike(last) || isVerbEnding(last)` のとき
  語尾種別に対応した fallback リストを使う
  - 動詞・形容詞末尾 fallback：`["が", "ね", "よ", "か", "ので", "けど", "から"]`
- bigram 学習が溜まれば自然に N-gram 候補が優先されるので、あくまで「初期状態の穴埋め」

**規模**: 数時間。

## カテゴリ G: UX ― 候補ウィンドウ

### G-1. 候補ウィンドウのセクション区切り ★★

**現状の問題**
候補リストが単一の縦並びで、「これは履歴」「これは予測」「これは辞書」の区別がつかない。
Shift+Delete が有効な行かどうかもユーザーには見えない。

**設計**
- `CandidateAction.show` はすでに `historyEnd` と `predictionEnd` を持っている
- `CandidateWindow` の `NSTableView` で区切りセルを挿入するか、
  `tableView(_:rowViewForRow:)` でセクション行に薄いグレーの区切り線を引く
- セクションラベル案：
  - `predictionEnd` 行の前：「予測」（グレー文字、選択不可）
  - `historyEnd` 行の前：「履歴」
  - それ以降：「辞書」
- 選択不可行の扱い：`tableView(_:shouldSelectRow:)` で false を返す、
  インデックスをスキップして矢印キーで飛ばす

**規模**: 数時間〜半日（CandidateWindow の改造）。

## カテゴリ H: 運用品質

### H-1. DB 自動 GC ★

**現状の問題**
`penalizeHistory` でスコアゼロのエントリは削除されるが、
「一度しか使っていない古い誤変換」が `used_at` の古いエントリとして永続的に残る。
長期使用で `history` / `bigram` テーブルが数万行に膨らみ、fetch 速度に影響する可能性がある。

**設計**
- アプリ起動時（または週次）に非同期でバックグラウンド GC を実行：
  ```sql
  DELETE FROM history WHERE count = 1 AND used_at < (now - 180 * 86400);
  DELETE FROM bigram  WHERE count = 1 AND used_at < (now - 180 * 86400);
  VACUUM;
  ```
- `DatabaseManager` に `performGCIfNeeded()` を追加し `AppDelegate.applicationDidFinishLaunching` で呼ぶ
- 「最後に GC した日時」を UserDefaults に保存し、7 日以内は再実行しない

**規模**: 数時間。

---

### H-2. `successorImmediateThreshold` の設定画面公開 ★

**現状の問題**
デフォルト 5 は固定値。使用頻度の高い環境（大量タイピング）ではしきい値が低すぎて
まだ信頼できないペアが即時表示されてしまう可能性があり、逆に軽い使い方では
なかなか即時表示に昇格しない。

**設計**
- `SettingsWindowController` に「後続語の自動表示感度」スライダーを追加
  - 低（10）・中（5）・高（2）の 3 段階、または数値入力
- 値は `UserDefaults` に保存し `InputHandler.successorImmediateThreshold` を動的に読む
  - 現在 `static let` なので `static var` に変更が必要

**規模**: 数時間。

## 実装順序の推奨

| 段階 | アイデア | 理由 |
|------|---------|------|
| **即投入** | G-1（セクション区切り）+ H-1（DB GC） | コスト小・副作用なし・品質向上 |
| **第三弾候補** | E-1（Backspace 再変換） | IME としての基本機能。IMK 制約調査と合わせて計画化 |

| 第四弾 | F-2（セグメント bigram）+ F-3（isNounLike 拡張） | 変換精度の積み上げ |
| 別計画 | H-2（threshold 設定化） | ユーザーの調整ニーズが出てきたタイミングで |

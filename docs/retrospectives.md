# 開発判断・運用のメタルール

個別の機能判断（`rejected.md`）を振り返って抽出した、普遍的に使える開発・運用のルール集。
「なぜそう判断するか」を残すことで、次回同じ局面で同じ考察をやり直さなくて済むようにする。

プロダクトの差別化軸・「何を作るか」の判断は [`concept.md`](concept.md) を参照。本ファイルは「どう作るか・どう運用するか」のメタルール限定。

**読み返すタイミング**: 新機能の実装前・大きなリファクタリング前  
**更新するタイミング**: `rejected.md` に新しいケースを追記したとき、または原則を破って後悔したとき

---

## ローマ字分解は表記・OS 一般論・UI を混同しない

ローマ字 IME の議論では **打鍵列の逐次分解**（`RomajiConverter` + テスト）だけを正本にする。次の 3 つは別物として扱う。

1. **表記** — Hepburn 等の英字綴り（パッケージの `konnyaku` = こんにゃく、等）
2. **分解規則** — 打鍵を 1 文字ずつ変換した結果（`konnyaku` → こんやく）
3. **UI** — marked text に何を見せるか

**なぜ**: LLM は「`nn` → ん」の口诀と表記 corpus から、存在しない「`nn` 後の hidden `n`」状態機械を合成しやすい。OS 名を冠した「標準 IME 準拠」も検証なしに増殖する。実装前に **`konnyaku` を trace して こんやく になるか** を確認しないと、表記ベースの誤仕様が入る。

*由来: `hiddenPendingN`（R-1）— `konnyaku` が こんにゃく に化け 婚約 に届かなかった。表記・OS 模倣・Converter pending の混同が原因*

## UX の検証を実装前にやる

複雑な実装に入る前に、「トリガーとなるキー操作がタイピングの流れに乗るか」を手動シミュレーションや最小プロトタイプで確かめる。

**なぜ**: IME の機能は「動く」ことより「自然に使える」ことの方が難しい。実装コストをかけた後で UX が合わないと判明すると、削除コストも高くなる。

*由来: Successor モード（F-1）— タイピングリズムと合わないと判明したのが実装後だった*

---

## フラグが多くのファイルをまたぐときは立ち止まる

1 つの機能フラグ・状態変数が `InputHandler`・`InputController`・`AppDelegate`・デバッグ系など複数コンポーネントに波及しているときは、「この機能は本当に必要か」を再確認するタイミング。

**なぜ**: 依存の広がりはその機能の責務が曖昧であることを示すことが多い。広がったまま進めると削除コストも比例して大きくなる。

*由来: Successor モードの `successorEligible` / `successorBufferedRomaji` が広範囲に散在していた*

---

## 呼び出し箇所がなくなったコードはその場で消す

関数・フラグ・通知名の定義が残っているのに呼び出し箇所がない場合は、機能変更のタイミングで即座に削除する。

**なぜ**: dead code は将来の読者を惑わせ、削除作業時のノイズになる。「後で消す」は消されないことが多い。

*由来: `postSuccessorPendingNotification` が定義だけ残って誰にも呼ばれていなかった*

## 「記録」と「照会」は疎結合にしておく

学習データの蓄積ロジック（`POSCommitSequencer`・`DatabaseManager+Ngram` 等）と、それを利用する予測ロジックは別レイヤーに分ける。

**なぜ**: 予測の方式が変わっても学習データは捨てなくて済む。逆も然り。疎結合にしておくことで、片方だけ差し替え・削除ができる。

*由来: Successor モード削除時、bigram 記録ロジックを一切触らずに予測部分だけ削除できた*

## ドキュメントはコードから引き出せない情報限定

`docs/` 配下に書くべきは「コード読解では再構成できない情報」のみ。理由・哲学・経験的失敗（`rejected.md`）・俯瞰図（`states.md` の Mermaid）・外部システム制約（`apple-intelligence.md`）が該当。**用語定義・behavior spec・入力シナリオはコードと重複するので書かない**——変数宣言の `///` ドキュメントコメントとテストが正本になる。

**なぜ**: 同じ情報を 2 箇所に書くと drift する。コードは実行されるので嘘になりにくいが、ドキュメントは嘘でも警告が出ない。drift したドキュメントは「無い」より悪い——能動的な誤情報になり、新規参入者の理解を間違った方向に向ける。

*由来: glossary.md L117 が `recordPrefixes` について「前方一致パターンも記録」と書いていたが、実コードは「フル読みのみ」記録。完全に逆の主張。glossary.md / scenarios.md / architecture.md の削除コミット（`a95512d` / `124ce3e`）参照*

## memory・ドキュメントを引用する前に grep verify

memory・ドキュメントに書かれた識別子（関数名・フラグ名・テーブル名）を発話・推奨に使う前に、コードベースに grep して **現在存在することを確認** する。memory はファイル冒頭に「point-in-time observation」と明記されており、ドキュメントも drift しうる。

**なぜ**: 「memory に書いてあった」「ドキュメントに書いてあった」は「過去のある時点で真だった」を意味するだけで、「今真である」とは限らない。verify せずに発話すると、削除済み機能を現役として説明する事故が起きる。

*由来: Session 開始時、stale な memory（23 日前作成）を引用して「Successor モードが keynaco の特徴」と説明したが、Successor は 2026-05-25 に削除済みだった。memory ファイル自体に「verify against current code」と明記されていたのに読み飛ばした*

## `///` コメントは WHAT ではなく非自明な WHY/HOW

変数宣言・関数定義に付ける `///` ドキュメントコメントは、コードから自明な「何をするか」ではなく、ソース読解では拾えない「なぜそうするのか」「どう使われるのか」「壊してはいけない不変条件は何か」を書く。

**なぜ**: WHAT は識別子名と実装が既に表現している。非自明な WHY / HOW を書かないと、リファクタ時に invariant を破る変更が入って、後で気付く頃には history を辿らないと理由が分からなくなる。`fetchHistoryScoredMerged` の「SUM 集計を分割禁止」のような anti-pattern 警告がこれに該当。

*由来: glossary.md / scenarios.md 削除時、behavior spec をコード側 `///` に救出した経験。`isExplicitlySelected` の「`true` で文字キーが選択確定をトリガー」のような **使い方の意味** は識別子名だけでは伝わらず、コメントが要る*

## 外部依存を足すか判断する前に実物（形態・権限・entitlements）を確認する

外部コンポーネントを「依存に足すか」検討するときは、README の機能説明から依存形態を推測せず、**実体を見る**——SwiftPM ライブラリかスタンドアロンアプリか、要求する権限（Accessibility 等）、`.entitlements`（サンドボックス可否・App Group）、ライセンス。これらが分かって初めて「足せるか」「ポジショニングと整合するか」を判断できる。

**なぜ**: README の「○○対応」は機能の話であって、配布形態・権限・信頼契約の話ではない。推測で「ライブラリとして足せそう」と進めると、実は非サンドボックスアプリで全画面テキストを舐める設計だった、のような前提崩壊が後段で露見する。権限とサンドボックスはプロダクトの信頼契約に直結するので、機能の魅力より先に確認する。

*由来: Zenzai personalization のデータ基盤として Tuner を検討（G-2）。README の「personalization 対応」から依存候補と思って見に行ったら、実体は `app-sandbox: false` で Accessibility により全アプリの画面テキストを常時スクレイピングする独立アプリだった。entitlements と .xcodeproj を実物で確認したことで「ローカル完結」ポジショニングとの衝突を判断でき、却下に至った*

## 計測結果は「桁が物理的に妥当か」を先に確認する

自作の計測ハーネスやベンチの結果を結論に使う前に、**数値の桁が既知の挙動・物理と整合するか**を確認する。「LLM 推論が 5ms」「本番で出るはずの候補が 0 件」のように、実機の振る舞いと矛盾する数字が出たら、結論ではなく**計測セットアップを疑う**。論理的な矛盾だけでなく、桁・速度・件数の妥当性まで見る。

**なぜ**: 自作ハーネスは本体を不完全に模すため、失敗が crash ではなく**サイレントな嘘の数字**として出る。質の悪いのは「もっともらしく見えて根拠が間違っている結論」——たまたま正しい判断に近い値が出ると気づけず、間違った理由で正しい結論を出してしまう（後から前提が崩れると総崩れになる）。桁の sanity check は frontでフルスイープを回す前に1回分で済むので安い。

*由来: POC260529c で inferenceLimit を計測した初回、ZenzaiCache 短絡で全 limit が 5-8ms 一定・候補不変になり「非レバー（何も効かない）」と結論しかけた。「70MB モデルの推論が 5-8ms はあり得ない」で気づき、fresh converter で測り直したら実際は難ケースで cap が効いていた（結論は「5 で十分」と同じでも理由は真逆）。同セッションでもう1度、予測候補の composingCount を測る harness が `ComposingCount.composite` ケースを落として全候補 count=0 を返し、「フィルタで全部 strip される」と誤判定しかけた（本番が動いている＝0 はあり得ない、で発覚）*

## 候補リストの振る舞いはユニットテストを正本にし、sandbox は手順付きで補助する

`CandidateSectionBuilder`（PLAN260624 で `CandidateScoreBuilder` に置換済）・履歴枠・辞書重複排除のような**リスト組み立て**の変更は、まず builder の単体テスト（stub 入力）で再現ケースを書く。sandbox は E2E の補助で、`seed_history` → 変換 → `candidateEntries.section` の確認に使う。

**なぜ**: リスト組み立ては純粋関数に近く、ユニットテストが速くて決定的。sandbox は AzooKey 実辞書・非同期 prefetch・Zenzai に依存し、手順を誤ると「実装バグ」に見える嘘（辞書候補が 2 件だけ等）を返す。正本と補助の役割を分けないと、修正が正しくても sandbox だけ失敗し続ける。

*由来: 前方一致履歴の top3 漏れ語が辞書から消える修正（`c73e8d9`）。ユニットテストは即 PASS だが、sandbox では `then: "space"` 一発＋存在しない検証語（`感情`）で誤 FAIL。`wait_azoo_key` 挟み＋辞書存在確認後に再測で PASS*

## 修正の「目的範囲」と「実装範囲」のミスマッチを警戒する

具体的な 1 ケースを直すために**広めの述語で実装する**と、目的外のケースまで巻き込んで副作用バグを生む。コミットメッセージが「X が Y より前に」のような具体目的を書いとるのに、実装が「単セグメント完全一致全部を先頭プロモート」のような **広い条件式**になっとったら、目的外のケースで何が起きるかを 5〜10 入力で先に確認する。post-process を入れる前後で**生候補リストの top-N がどう変わるか**を実機で並べて見るのが最短。

**なぜ**: 「狭い目的に対して広い実装」は意図したケースを直すと同時に、想定外のケースを引っ張り込む。実装を書いた人は「内閣府を上に」しか頭になかったが、述語 `data.count == 1 && rubySum == inputLength` には機械生成カタカナ・ひらがな・大文字 ASCII などが全部該当する。テストは元の目的（内閣府）しか保護してないので、副作用は緑のまま見過ごされる。広い述語を書くなら「これに該当する候補は他に何があるか」を**列挙**してから判断する。

*由来: `eb5e31b`「`ないかくふ → 内閣府`が「内閣府令」より前に来るようにする」という具体目的の修正が、`data.count == 1 && rubySum == inputLength` を exact 枠でプロモートする実装になっていた。その結果、AzooKey の `getAdditionalCandidate` が生成する機械生成カタカナ・ひらがな候補（同じ述語に該当）も exact 枠に乗って、「カクニンガヒツヨウデスネ」「かくにんがひつようですね」が「確認が必要ですね」より上に来る事故が発生。修正コミットメッセージには「内閣府」しか書かれてなく、副作用範囲の検証なし。後に `5b192e5`（カタカナ除外）と `ea50b1a`（ひらがな除外）で 2 段階で穴埋め*

## 内部ロジックを疑う前に最外側の post-processing を bypass して観測する

「実機の振る舞いとコード読みが乖離する」とき、AzooKey のような提供側ライブラリの内部を読む前に、**呼び出し側の最外側 post-processing を一行 bypass** して提供側の生戻り値を観測する。filter・ソート・並び替え・プロモート系の post-process は keynaco 側にいくつも積み上がっており、どの段でズレてるかを直接見るのが一番速い。

**なぜ**: keynaco 側で何段もの post-process（`filterCandidatesForDisplay` → `sortAzooKeyCandidates` 等→ `CandidateSectionBuilder` → `InitialRowPolicyResolver` …。`CandidateSectionBuilder` は PLAN260624 で `CandidateScoreBuilder` + `CandidateScoredLayout` に置換済）が AzooKey の戻り値を変形している。「AzooKey が悪いか keynaco が悪いか」は、内部読みより **最外側を一個ずつ無効化して観測**する方が決定的。Zenzai モデル / 文脈 / ライブラリ revision の比較は数十分かかるが、一行 `return candidates.map { ... }` は数分。試す順序を逆にすると無駄が積み上がる。

*由来: 長文ひらがなでカタカナが Z1 になる問題で、v3.1 ↔ v3.2 モデル比較・leftSideContext 比較・Zenzai OFF と段階的に切り分けて「AzooKey ライブラリ起因」と確定しかけたが、ユーザーから「これは AzooKey のランク問題ではなく keynaco 側の後処理の問題だということ？」と指摘されて `filterCandidatesForDisplay` を一行 bypass。生 AzooKey 順では「確認が必要ですね」が Z1、カタカナは下位だと判明し、`eb5e31b` の exact プロモートが真因と一発確定（`5b192e5`/`ea50b1a`）*

## テストは「実装の選択肢」じゃなく「ユーザー体感」をアサートする

「Space は `.selectNext` を返す」のように **実装が返す enum ケースを直接アサート**するテストは、その実装を変えたい時に道連れになる。アサートは可能な限り **「ユーザーが画面でどう感じるか」**（ここでは「Space 一発で Zenzai が推した Z1 が確定する」）に一段抽象を上げる。実装の選択肢をアサートする必要があるときは、最低でも別途「ユーザー体感」テストとセットで書いて二重で保護する。

**なぜ**: 実装レベルのアサートは「その実装が今動いている」ことしか言わない。ユーザー体感が壊れていても、実装が当初の選択肢を返している限り test は緑で通る。実装の選択肢が間違っとった場合、テスト自体が誤仕様の保護役になってバグを通過させる（「過去の fix コミット＋保護テストの組み合わせは『バグ仕様』として固着しうる」と同根、再発予防の側）。

*由来: `testSpaceDuringCandidatesSelectsNextWithoutRebuild`（候補表示中の Space は `.selectNext` のはず）が、AzooKey 自動表示中の Space で Z1 ひらがなを素通りして Z2 カタカナが確定するバグを保護していた。`24bd9e9` で実装を `.explicit` リビルドに変えるとテストが壊れたが、書き換えてみたら **ユーザー体感を守るテストが一件も無かった**ことが判明。新規 2 件（自動表示中 / 明示選択後）で書き直し*

## キーの意味は文脈依存——`isExplicitlySelected` で「次候補」と「明示変換要求」を分ける

候補ウィンドウ表示中の Space を「次候補」と一律に解釈する設計は、AzooKey が**自動表示した候補**にも適用されて意図しない確定を引き起こす。**ユーザーが一度も明示選択していない状態（`candidateSession.isExplicitlySelected == false`）の Space は「次候補」ではなく「明示変換要求」**として扱い、`buildCandidateList(.explicit)` で initialRow=0 から再開する。↓・Tab・Space のうちユーザーが触ったあと（`true` 移行後）は通常通り `.selectNext` に進める。

**なぜ**: 「候補表示中」と「ユーザーが候補を見て選んだ」は別。AzooKey 非同期 fetch 完了で自動的に候補窓が出るパスがあるため、画面に見えている＝ユーザー意図、と短絡できない。`isExplicitlySelected` フラグはこの区別のためにある。これを参照せずキー操作を分岐すると、自動表示の Z1 を Space で素通りする事故が起きる。

*由来: `24bd9e9` のバグ修正。`KeyDispatch.route` で `candidateVisible=true` → `.candidateVisible` → `.selectNext` の流れが、`isExplicitlySelected=false` の状態でも発火していた。Zenzai 順序を上書きする lcid ソート（[`rejected.md` P-7](rejected.md)）を消した直後も依然「ヤバイ」「マジ」「成程」が選ばれ続けた原因*

## サイレントな品質劣化はログ計装なしには気づけない

「Zenzai が推した Z1 と実確定が食い違う」のように **画面では見えるが事故として捕捉されていない**事象は、計測を仕込んで初めて発見・改善できる。新しい予測・並び替え・選択ロジックを入れるときは、その**判断が外れたケースを 1 行 jsonl に残す**観測経路をセットで設計する。普段はノイズ最小（不一致のみ記録）、後追い分析できる粒度を残す（reading・Z1・confirmed・was_explicit・candidates）の二点を満たす。

**なぜ**: latency・キャッシュヒット率のような連続メトリクスは閾値超過で気づけるが、「選択ロジックの判断が外れた」は離散事故で、ユーザーが報告しない限り見えない。報告ベースだと「件数感」が掴めず、改善の優先度判断ができない。ログがあれば「`was_explicit=false` の事故率」「`was_explicit=true` で実確定がひらがなだった件数」のサマリで Zenzai の苦手パターンが定量化できる。

*由来: lcid ソートが Zenzai を逆転していたバグ（[`rejected.md` P-7](rejected.md)）も、自動表示中 Space の素通り問題（`24bd9e9`）も、ユーザーが体感で気づくまで放置されていた。`009ba9a` で `divergence_log.jsonl` を導入し、今後の Z1 不一致は全件ログに残るようにした。観測基盤を後付けで足すと過去のデータは戻ってこないので、新ロジック導入と同時に計装する*

## 過去の fix コミット＋保護テストの組み合わせは「バグ仕様」として固着しうる

「以前のバグ修正コミット」と「その挙動を保護するテスト」が両方残っていても、それは「現在の挙動が正しい」ことを意味しない。**部分修正がテストごとバグ仕様として固着しただけ**の可能性がある。継承するコードでルールに違和感を覚えたら、git log でその fix の意図を読み、「**そのルールがそもそも要るか**」「**消したら何が困るか**」を実機で確かめてから手を入れる。

**なぜ**: 「テストが保護している ⇒ 仕様」と短絡しがち。だが部分修正は「直したいケースは直したが、別のケースは依然壊れている」状態で commit されることがあり、保護テストはその不完全な状態を固定化する。新しいバグ報告（「シャツが出ない」等）が来たとき、テストを正本として扱うと「仕様通り」と誤判定して根本に到達できない。「修正コミット + テスト」を見たら「これは固着したバグ仕様ではないか」を一度疑う。

*由来: `しゃつ → シャツ` が候補に出ないバグ調査。`bf57684`「未知語でカタカナ候補が候補ウィンドウに表示されないバグを修正」が `hasRealCandidates=false`（未知語）だけ救出し、`hasRealCandidates=true`（既知語＋珍辞書語）のケースは依然消える状態を残したまま、`testKnownWordWithZenzaiDoesNotShowKatakanaInMainList` で「変換候補があるときカタカナ除外」を保護していた。最初は私もこのテストを正本として「カタカナ末尾固定を別経路で復活させる」方向に進みかけたが、ユーザーから「そのルール自体に意味があるのか」「独立したカタカナ固定は必要か」と段階的に問われ、実機で AzooKey の挙動を 8 ケース測ったら既知語は AzooKey 自身がカタカナを返していて末尾固定の存在意義が薄いと判明。「末尾カタカナセクションそのもの」を撤廃して AzooKey 出力に一本化（`cb05019`、35 行追加 / 89 行削除）*

---

## フォールバックを撤廃するときは「同じ条件分岐に乗っとった明示意図ロジック」を実機で再点検する

暗黙のフォールバック（保険的にひらがな先頭固定する等）を撤廃するとき、ユニットテストが全部緑でも安心しない。同じ if 文の枝に依存して動いとった「明示意図ロジック」（hiraganaPreferred のような、ユーザーが意図的に有効化した経路）が、フォールバック撤廃に伴う dismiss 条件追加で巻き込まれて落ちる可能性がある。**実機 sandbox で機能境界の挙動を再点検する**。

**なぜ**: フォールバック撤廃の判断は「フォールバックが消えても OK」を確認する。だが「フォールバックと同じ条件分岐に依存しとった別経路」までは撤廃の判断対象に入ってない。ユニットテストは個別経路を独立に検証することが多く、「同じ if 文の枝に複数経路が乗っている」状態は捕まえにくい——独立に書いたテストは個別に通っても、本番で同時実行されると意図しない経路が dismiss に流れる。境界の確認は実機が一番速い。

*由来: `addsDefaultFixedHiragana` 撤廃（`7986157`）で `whileTyping` の早期 dismiss 条件を追加したとき、最初 `fixedSlot == .none` のガードを忘れた。ユニットテスト全緑だったが、実機 sandbox で `no`/`wo`/`toka` を打つと、hiraganaPreferred 経路（`の`/`を`/`とか` は builtin で明示的にひらがな優先）まで dismiss されて Enter で `の` が確定できなくなっとった。修正で `fixedSlot == .none` を dismiss 条件に追加し回復。同じ if 文の中に「フォールバック撤廃で消したい経路」と「明示意図で残したい経路」が同居しとった*（注: `fixedSlot` は PLAN260624 で削除済。現コードでは `hiraganaBonusKind` がひらがな優先のスコア加算を担う）

`keynaco-ime-sandbox` で `len(candidates)` がベースライン（シードなし）と比べて極端に少ない（例: 十数件 → 2 件）とき、まず `type_string` → `wait_azoo_key` → `key: space` の順になっているか確認する。Debug ソケットは `deferAzooKeyWhileTyping = true` のため、`seed_history` 直後の `then: "space"` 一発は prefetch 未完了のまま Space が走りうる。

*由来: 上記 `c73e8d9` の sandbox 検証。`seed_history` 後に `type_string`+`space` 一発だと辞書が `カンジ` 1 件だけに見えたが、`wait_azoo_key` 後は 19 件に復帰*

# スキル創造・運用の原則

`.claude/skills/` 配下のスキルを作るときの判断軸。`docs-audit` / `plans-audit` を作る過程で抽出した。

---

## スキルを書いたら確定前に 1 回 dogfood する

新スキルの SKILL.md（特に手順・triage ガイド）を確定する前に、**自分で 1 回最後まで通す**。スクリプトを実走し、出力を読み、SKILL.md の指示通りに 1 件だけ作業してみる。

**なぜ**: スキルの手順は **使ってみて初めて使えなさが分かる**。「triage を 1 セッション 5-10 件ずつ」のような指示を、自分で 1 件すら triage せずに書くと、現実離れした手順が固定化される。後で読み返した人（or 別セッションの Claude）が「書いてある通りやってもうまくいかない」と感じる。

*由来: `plans-audit` の SKILL.md に「triage 1 セッション 5-10 件ずつ」と書きながら、自分では 0 件しか backfill していなかった。triage 体験が空想だったため指示の説得力が弱い*

---

## DRY は rule of two（2 つ目で共通化する）

`scripts/` 配下で同じロジックが 2 ファイル目に出てきた瞬間、**3 ファイル目を待たずに `lib.sh` に抽出する**。「3 つ揃ってから」ではなく「2 つで動く」が境界。

**なぜ**: スクリプト群はドキュメント以上に drift しやすい（同じ AWK ブロック 3 箇所に書くと、1 つだけ修正して他が古いまま、になる）。2 つ目で共通化を済ませると、後続の 3 つ目以降は自然に lib を呼ぶ。3 つ並んでから共通化すると refactor リスクが上がるし、後回しになる。

*由来: `plans-audit` で frontmatter パース AWK を 3 つのスクリプトに書いてから `lib.sh` に抽出した。最初の 2 ファイル時点で抽出していれば 3 ファイル目を書くときの労力が減っていた*

---

## 数値主張は SKILL.md / docs に固定値で書かない

「N テーブル」「M タブ」「72 件の legacy plan」のような数値は **ドキュメントに固定値で書かず、スクリプト出力に任せる**。書くなら「数十件規模」「多数」のような曖昧表現に留める。

**なぜ**: 数値は実装変更で真っ先にズレる。固定値を書くと drift が嘘になり、次に読む人を能動的に誤誘導する。`docs-audit` の `check_counts.sh` が検出しているが、そもそも書かなければ drift しない。

*由来: `plans-audit` の SKILL.md L48 に「72 件以上の legacy 状態がある」とハードコードしていた。あと数ヶ月で 100 件超えると drift する。レビューで指摘されて「数十件規模」に修正*

---

## スキルを書いた直後に skill-creator レンズで自己レビューする

新スキルを書いた直後（≦ 1 時間以内）に、skill-creator のチェックリスト（description triggering / progressive disclosure / WHY コメント / bundled scripts / 絶対パス / DRY / 自己 drift）で 1 周見る。

**なぜ**: 書いた直後は「動いた満足感」で雑に終わりがち。第三者レンズ（skill-creator）を当てると **High 2-3 件・Medium 2-3 件** は確実に出る。レビュー観点が言語化されていれば 2 回目以降は速くなる——技能化する。

*由来: `docs-audit` 第 1 版が絶対パスハードコード・インライン bash 散在・誤検出 63 件だった。skill-creator レビューで 4 項目改善 → 誤検出 7 件に。`plans-audit` 第 1 版は同じレビューで 5 項目改善（SKILL.md と実装の drift・DRY 違反等）*

---

## ログの「フラグ」と「UX 損失」を混同しない

ログには 3 種類ある。性質が違うので **1 つだけで結論を出さない**。

| ログ | 性質 | 単独で結論を出すと… |
|------|------|------------------|
| `latency_log.jsonl` | 速度の指標 | 速い／遅いは分かるが「ユーザーが困ったか」は分からん |
| `divergence_log.jsonl` | Zenzai Z1 がズレたフラグ | **ユーザー視点の損失とは限らない**。履歴・辞書がカバーしとるケースを含む |
| `input_log.jsonl` | 実際の打鍵コスト（BS / scroll / composition_ms） | これが UX 真実に最も近い |

**手順**: 真に直すべきケースは `input_log` の `bs_count >= 2` ・`scroll_count > 0` ・`composition_ms > 3000` あたりで抽出する。`divergence_log` はそこに紐付く参考情報として読む。

**なぜ**: `divergence_log` だけで「Zenzai が外したケース」を全て UX 問題と見なすと、実際は履歴/辞書が救って自動確定しとるケース（= IME が健全に動いとる証拠）まで「直すべき問題」に分類してしまう。今回プロファイリング調査の最初のターンでこの誤読をやって、危うく価値ある履歴（しょり→処理 count=18 等）を「汚染」として削除しかけた。

*由来: 2026-06 プロファイリングセッション。`divergence_log` を「Zenzai が外した = UX 損失」と解釈して履歴 cleanup を計画したが、DB を直接見て初めて「Z1 がしょりと推した一方で履歴の処理が row 0 を取って救った」事実を確認。`rescued_by` フィールドを追加（`was_explicit=false` のとき `confirmed_source` を入れる）して、次回からログ読みの段階で「救われたケース」と「真の UX 損失」を区別できるようにした*

---

## destructive な DB 操作の前に SELECT で中身を確認する

履歴 DB の cleanup スクリプトを実行する前に、**削除対象の SELECT 結果を必ず目視する**。`--apply` 前の dry-run 件数だけでは判断材料として足りない。

**なぜ**: ヒューリスティック（例: `input == output のひらがな`）でフィルタすると、汚染と判別不能な「正しい学習エントリ」が混入する。「のびしろ → 伸びしろ (count=11)」「ありがとう → ありがとう」みたいな、表面パターンは同じだが意味が全く違うエントリを一律削除しかねない。dry-run で「295 行が対象」と出ても、その 295 行に何が入っとるかは別問題。

*由来: 2026-06 プロファイリングセッション。divergence ログ誤読（前項）と組み合わさって、ひらがなパススルーらしき履歴 295 行を一括削除する寸前まで進んだ。SQLite を直接 SELECT したら、削除候補に「のびしろ → 伸びしろ (count=11)」のような価値ある学習が含まれとった。`--apply` する前にユーザーが「任せる」と言うていたが、それでも本人が中身を見れたのは偶然だった*

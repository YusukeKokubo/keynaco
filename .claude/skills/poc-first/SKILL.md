# POC-first: 実装前の仮説検証

実装に入る前に「本当にこの機能は価値があるか」を最小のコストで確かめる。

**なぜ重要か**: keynaco の改善アイデアは AzooKey / Zenzai がすでに解決していることがある。また、
実装が簡単なほど POC なしで入りやすく、後で「本当に効いているか？」が不明なまま残りやすい。

## Step 1: 仮説を言語化する

以下を明示する:

```
【機能】何を実装しようとしているか

【課題】今どんな不便があるか（具体的なシナリオで）

【仮説】この機能を入れると X が Y になる

【前提条件】仮説が成り立つために必要な条件
  例: 「候補1位が意図通りでないケースが頻発している」
       「履歴・Zenzai では拾えない読みパターンがある」
```

**前提条件が「たぶん〇〇のはず」という推測なら、そこを先に sandbox で確認する。**

## Step 2: 最小の検証を設計する

| 検証したいこと | 使うツール |
|---|---|
| 前提条件の機能がすでに実装済みか | **コードを読む**（最初にやる。既存実装の発見が最速） |
| IME の変換・候補の動き | `keynaco-ime-sandbox` スキル |
| 入力ロジックの単体動作 | `cd Core && swift test` |
| 履歴候補の出方 | sandbox で `seed_history` + 入力シーケンス |
| 括弧モードなど特殊モード | sandbox で `isBracketMode` を確認 |

**検証の合否基準を先に決める**: 「〇〇が確認できれば実装する、△△なら実装しない」を言葉にしてから検証を始める。

## Step 3: 検証を実行する

sandbox での典型パターン:

```python
send({"reset": True})
r = send({"type_string": "...", "then": "space",
          "fields": ["candidates", "selectedText", "historyEnd", "fixedEnd"]})
print(r["candidates"][:5])  # 前提条件を確認
```

結果を記録する:

```
【検証結果】
- ケース1: ... → 結果: ...
- ケース2: ... → 結果: ...
【結論】仮説は成り立つ / 前提条件が崩れた / 別アプローチが必要
```

## Step 4: 判断する

| 判断 | 条件 |
|---|---|
| 実装する | 仮説が成り立つことが確認できた |
| 実装しない | 前提条件が崩れた（例: AzooKey がすでに解決している） |
| 別アプローチ | 仮説は成り立つが実装コストが見合わない |

**価値が不明確なまま実装する場合は** `docs/observation.md` に卒業条件・廃止条件を書いてから入る。
価値が明確なバグフィックスや小さな改善は observation.md 不要。

## よくある落とし穴

**「簡単そうだから」で POC を飛ばす**  
実装が3行でも効果がゼロなら無駄。既存の `recordPrefixes` / 候補組み立てと重複していないか、コードを読んでから検証する。

**AzooKey / Zenzai がすでに解決しているケース**  
過去の経験: 「しんじゅくえき」「とうきょうとちじ」は AzooKey が1フレーズで変換済みだった。
sandbox で実際の候補を見てから判断する。

**1候補を決め打ちした検証**  
AzooKey の候補順は文脈・履歴で変わる。「1位が〇〇になるはず」という前提で検証しない。

**効果測定の設計を実装後に考える**  
「動いた」だけでは価値の判断ができない。実装前に「何が変われば成功か」を決めておく。

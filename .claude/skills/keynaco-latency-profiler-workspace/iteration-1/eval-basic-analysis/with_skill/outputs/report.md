## 問題の整理

### 問題 1: 2〜3 文字読みのキャッシュ miss 率が高い（重要度: 高）

ミス率 93.5%（2文字）・53.6%（3文字）は構造的に毎回 AzooKey + Zenzai を呼び出している状態に近い。キャッシュ LRU 上限（50 件）に対して 2〜3 文字読みの種類が多すぎる、あるいは leftSideContext 修正が想定どおり機能していない可能性がある。

**確認アクション**: `/keynaco-ime-sandbox` で 2 文字入力（例: `ka`, `ko`）を複数回送り、`peekCachedCandidates` が exact/prefix のどちらで返るか確認する。

### 問題 2: fetch_complete_p95 ≥ 300ms のセッションが 23.5%（重要度: 高）

スキル定義の閾値（> 20%）を超えている。ワーストセッションの fetch_p95 が 260〜376ms になっており、Zenzai 推論の外れ値が主因と考えられる。

**確認アクション**: `fetch_p95_by_reading_len` を読み長別に集計できるログデータがあれば、特定読み長への偏りを確認する（現スクリプトでは読み長別ミス件数の絶対値出力が `—` になっているため、スクリプト側で集計追加が必要かもしれない）。

### 問題 3: 実効 debounce 待ちが設定値より 35ms 超過（重要度: 中）

設定 70ms に対し実測中央値 104.6ms。パイプラインオーバーヘッドが常時乗っている。inter_key p50 が 104.7ms であり、debounce 設定（70ms）との差は小さいが、一部の打鍵が待ちに入って遅延している可能性がある。

### 問題 4: peek_update p95 が 42ms（重要度: 低〜中）

通常 1〜5ms のはずが中央値で 42.5ms のスパイクがある。GCD キュー競合か UI スレッドのブロックが散発している可能性がある。ただし p50 は 2.1ms と正常なので、外れ値の発生頻度は低い。

## 推奨アクション

優先度順に 3 点挙げる。

1. **2文字読みキャッシュの実挙動確認**: `/keynaco-ime-sandbox` で `type_string` + `state` を繰り返し送り、同じ 2 文字読みで exact hit が起きるか確認する。eviction が原因なら LRU 上限の引き上げ（50 → 100〜200 件）を検討する。`AzooKeyConverter.swift` のキャッシュキー実装も照合する。

2. **Zenzai 外れ値の読み長別集計**: 現スクリプトの `miss_count_by_reading_len` が `—` になっているため、`TypingLatencyStats` のログ構造を確認して `fetch_p95_by_reading_len` を取り出す。特定の読み長に偏っていれば Zenzai 処理量の問題、ランダムならスレッドスケジューリングや `llama_context` 競合を疑う。

3. **候補選択行動の計測補完**: 1位確定率が n=1 しかなく精度評価ができていない。`candidate_confirmations` が記録されるセッションが増えるまで実使用を継続するか、ログの記録条件を確認する。

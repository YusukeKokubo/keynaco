## エグゼクティブサマリー

変換候補が画面に表示されるまでの体感時間（`fetch_complete`）の中央値は **195 ms**、p95 は **273 ms**。内訳はデバウンス待機が約 100 ms、AzooKey＋Zenzai 推論が約 96 ms で、二つがほぼ均等に寄与している。キャッシュミス率が 50% と高く、読み長2文字での miss が恒常的に 93〜100% に達している。これが fetch を頻発させる主因。

## 1. fetch_complete（ユーザー体感レイテンシ）

`fetch_complete` はキー入力からデバウンス待機を経て候補が確定するまでの全体時間。

| 指標 | p50（セッション中央値） | p95（セッション p95） | 最大値 |
|------|------------------------|----------------------|--------|
| fetch_complete p50 | **195 ms** | 273 ms | 462 ms |
| fetch_complete p95 | **237 ms** | 396 ms | 525 ms |

`fetch_complete_p50` の分布（100 セッション）:

- 150〜200 ms: 55 セッション（55%）
- 200〜250 ms: 32 セッション（32%）
- 250〜300 ms: 8 セッション（8%）
- 300 ms 超: 4 セッション（4%）

**常に 150 ms 超**。100 ms 未満のセッションはゼロ。

## 2. レイテンシの内訳

`fetch_complete ≈ 実際のデバウンス待機 + fetch（AzooKey+Zenzai 推論）`

### 2-1. fetch（推論時間単体）

| 指標 | 値 |
|------|----|
| fetch_p50 のセッション中央値 | **95.9 ms** |
| fetch_p50 の p95 | 165.6 ms |
| fetch_p50 の最大値 | 375.5 ms |

fetch_p50 の分布:

- 50〜100 ms: 56 セッション（55%）
- 100〜150 ms: 35 セッション（35%）
- 150〜200 ms: 8 セッション（8%）
- 200 ms 超: 2 セッション（2%）

AzooKey 辞書引き＋Zenzai 推論だけで中央値 96 ms かかっており、改善余地がある。

### 2-2. デバウンス待機

| 指標 | 値 |
|------|----|
| 実際の待機（fc_p50 − f_p50）中央値 | **104 ms** |
| 実際の待機 平均 | 100.6 ms |
| 設定値（policy）の最頻値 | 70 ms |

policy=70 ms に対して実際の待機中央値は 102 ms と 30 ms 超過している。inter_key_p50 の中央値が 105 ms（実打鍵間隔）であり、デバウンスタイマーが打鍵ごとにリセットされた結果として追加の wait が積み重なっている。

デバウンス policy 別の fetch_complete_p50 中央値:

| policy | セッション数 | fc_p50 中央値 |
|--------|-------------|--------------|
| 45 ms  | 4           | 185.5 ms     |
| 70 ms  | 71          | 194.8 ms     |
| 105 ms | 9           | 199.5 ms     |
| 110 ms | 15          | 203.2 ms     |

policy を下げても fetch_complete の改善幅は小さい（fetch 自体が支配的なため）。

### 読み長別 miss 率（セッション平均）

| 読み長 | セッション数 | 平均 miss 率 | 中央値 |
|--------|-------------|-------------|--------|

| 4 文字 | 87          | 20.1%       | 0%     |

## 4. peek_update（UI 描画コスト）

候補ウィンドウの再描画時間（`peek_update`）は通常非常に高速。

| 指標 | 値 |
|------|----|
| peek_update_p50 の中央値 | **2.1 ms** |
| peek_update_p95 の中央値 | **42.4 ms** |
| peek_update_p95 の p95   | 50.4 ms   |
| peek_update_p95 の最大値 | 55.4 ms   |

中央値 2 ms は問題なし。ただし p95 が 42〜50 ms の範囲に集中している点が注目点で、セッション中に散発的に 40 ms 超のスパイクが起きている。peek 数が多いセッション（20〜69 peeks）でも p50 は 1.5〜2.6 ms に安定しているため、スパイクは発生頻度が低く peek 数とは無相関に見える。macOS の描画スケジューリングや他プロセスの割り込みによる確率的な遅延と推測される。

## 5. Zenzai の影響

`fetch_p95_zenzai_on` と `fetch_p95_ms` が 101/101 セッションで完全一致している。これは全セッションで最も遅い peek が Zenzai ON のものであったことを意味し、Zenzai が fetch レイテンシの上限を規定している。ただし、Zenzai OFF 時の比較データがないため、Zenzai 寄与分の定量的な分離はできない。

## 6. 外れ値の分析

**最悪セッション（16:41、fc_p50=462 ms）**: total_peeks=2、cache_miss=1、inter_key=203.7 ms、fetch_p50=375.5 ms。打鍵間隔が長くキャッシュが効かない状態で、fetch が 375 ms と通常の約4倍かかっている。一発起動（JIT コンパイル）やメモリ圧力など散発的な要因と考えられる。

**fc_p95 が 400 ms 超のセッション（4件）**: 13:09（新規起動直後）、16:41（上記）、13:33（1セッション目から数分後）の傾向があり、起動・ウォームアップ時のコールドスタートが疑われる。

## 7. ボトルネック優先順位

1. **fetch（AzooKey+Zenzai 推論）**: 中央値 96 ms。全体レイテンシの最大の寄与。読み長2文字での miss 率が 93% であり、短い読みのキャッシュ戦略（prefix キャッシュの再利用強化、先読みプリフェッチ）が有効。

2. **デバウンス待機**: 実際の待機は中央値 104 ms で policy の 70 ms を 34 ms 上回っている。inter_key が 105 ms 付近であり、タイマーリセットが連鎖している。policy 値の調整より fetch を速くする方が実効的だが、adaptive debounce（打鍵速度に応じた動的調整）も選択肢。

3. **peek_update p95 スパイク（40〜50 ms）**: 散発的で基本的には問題なし。体感への影響は小さいが、原因特定のために候補ウィンドウ描画の重い操作（`NSTableView` の reloadData タイミング等）を確認する価値はある。

4. **Zenzai コールドスタート**: 起動直後の fetch が 375 ms 超になるケースがある。初回推論の事前ウォームアップ（ダミー推論の実行）で改善できる可能性がある。

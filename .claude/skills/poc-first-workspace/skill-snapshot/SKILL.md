# POC-first: 実装前の仮説検証

実装に入る前に「本当にこの機能は価値があるか」を最小のコストで確かめる。

今日作った末尾助詞トリム拡張・フレーズ記録の教訓:
- フレーズ記録: 「AzooKey がすでに1フレーズで変換できる」ケースが多く、実装前に POC で確認すべきだった
- 末尾助詞トリム: 実装は簡単だったが効果の測定基準を後から考えた

## Step 1: 仮説を言語化する

以下を明示する:

```
【機能】何を実装しようとしているか

【課題】今どんな不便があるか（具体的なシナリオで）

【仮説】この機能を入れると X が Y になる

【前提条件】仮説が成り立つために必要な条件
  例: 「候補1位が意図通りでないケースが頻発している」
```

前提条件が怪しければ、そこを先に検証する。

## Step 2: 最小の検証を設計する

| 検証したいこと | 使うツール |
|---|---|
| IME の変換・候補の動き | `keynaco-ime-sandbox` スキル |
| 入力ロジックの単体動作 | `cd Core && swift test` |
| 履歴候補の出方 | sandbox で `seed_history` + 入力シーケンス |
| 括弧・Successor など特殊モード | sandbox で `isBracketMode` / `isSuccessorCandidateActive` を確認 |

**検証の合否基準を先に決める**: 「〇〇が確認できれば実装する、△△なら実装しない」

## Step 3: 検証を実行する

sandbox での典型パターン:

```python
send({"reset": True})
r = send({"type_string": "...", "then": "space",
          "fields": ["candidates", "selectedText", "historyEnd", "fixedEnd"]})
print(r["candidates"][:5])
```

結果を記録する:

```
【検証結果】
- ケース1: ...→ 結果: ...
- ケース2: ...→ 結果: ...
```

## Step 4: 判断する

| 判断 | 条件 |
|---|---|
| 実装する | 仮説が成り立つことが確認できた |
| 実装しない | 前提条件が崩れた（例: AzooKey がすでに解決している） |
| 別アプローチ | 仮説は成り立つが実装コストが見合わない |

判断したら `docs/observation.md` に「卒業条件・廃止条件」を書いてから実装に入る。

## よくある落とし穴

**「簡単そうだから」で POC を飛ばす**  
実装が3行でも、効果がゼロなら無駄。簡単な実装ほど POC なしで入りやすく、後で「本当に効いてるか？」が不明なまま残る。

**AzooKey / Zenzai がすでに解決しているケース**  
IME の改善アイデアは、変換エンジン側で既に対処していることが多い。sandbox で実際の候補を見てから判断する。

**1候補を決め打ちした検証**  
AzooKey の候補順は文脈・履歴で変わる。「1位が〇〇になるはず」という前提で検証しない。

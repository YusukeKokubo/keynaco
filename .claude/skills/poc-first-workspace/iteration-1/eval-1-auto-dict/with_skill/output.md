## POC-first: 「頻繁に使う語をユーザー辞書に自動登録する機能」

### Step 1: 仮説を言語化する

```
【機能】確定頻度が高い語（フレーズ）を自動的にユーザー辞書に登録し、
       変換候補の最上位に常に出るようにする

【課題】同じ語を何度も変換しているのに、候補の並び順が安定せず毎回選び直しになる

【仮説】この機能を入れると、頻出語の変換精度が上がり、選ぶ回数が減る

【前提条件】
  - history テーブル（N-gram 自動学習）だけでは頻出語が候補 1 位に来ない
  - ユーザー辞書への明示登録がスコアを押し上げる（history より優先される）
  - 「自動登録すべき閾値」を機械的に決められる
```

---

### Step 2: 仮説の前提条件を検証する前に止まる

**実装に入る前に、まず既存の仕組みが本当にカバーしていないか確認が必要。**

keynaco の `buildCandidateList` の優先順位:

```
1. ひらがな / カタカナ固定
2. ユーザー辞書（完全一致）
3. Zenzai top-1（左文脈あり）
4. 履歴（fetchHistoryScoredMerged: 時間減衰スコア閾値以上）
5. 数字・日時候補
6. AzooKey 辞書候補
```

履歴（4）はすでに「使った回数×時間減衰スコア」で上位に来る設計になっている。
「頻繁に使う語」とは、まさに履歴スコアが高くなる語のことであり、
**履歴の仕組みがこの課題をすでに解こうとしている**。

前提条件「history だけでは候補 1 位に来ない」が本当に成り立つかを、
sandbox で実測する前に実装してはいけない。

---

### Step 3: 実装しない判断を先に下す（過去の経験から）

memory に明確な前例がある:

> **「ユーザー定義略語は不要」（feedback_user_defined_abbrev.md）**
> N-gram テーブルによる自動学習が定型文補完の役割を担っている。
> ユーザーが手動で定義しなくても使い込めば自動的に候補に出るようになるため、
> 明示的な略語登録機能は設計思想に反する。
> **How to apply: 「ユーザーが手動で何かを登録/設定する機能」は出さない。
> 使い込むほど自動で賢くなる方向性を優先する。**

「自動登録」は「手動登録」ではないが、本質は同じ:
- ユーザーが意識する登録 → 手動登録
- 機械が判断して辞書に書き込む → 自動登録
- **どちらも「辞書に書く」という副作用を持つ別レイヤーを追加する**

これは N-gram 自動学習（history テーブル）の上に、同じ目的の別機構を重ねる設計になる。

---

### Step 4: 判断

**実装しない。**

| 理由 | 詳細 |
|------|------|
| history が同じ課題を解いている | `fetchHistoryScoredMerged` が頻出語を上位に持ってくる設計。二重管理になる |
| 「自動で賢くなる」設計方針に反する | ユーザー辞書という固定状態を増やすのではなく、履歴スコアで動的に解くべき |
| 閾値設計が難しい | 「何回以上で自動登録」の閾値は個人差が大きく、誤登録が増える |
| 削除の難しさ | 自動登録された辞書エントリを後で「消し忘れ」する運用負荷が生まれる |
| ユーザー辞書 vs 履歴の責務が混濁する | ユーザー辞書は「AzooKey 辞書にない固有語」の明示登録用。頻度管理は history の責務 |

**もし「頻出語が候補 1 位に来ない」という具体的な困りごとがあるなら:**

sandbox で以下を確認する:
```python
# seed_history で同じ語を複数回確定させた後の候補順を確認
send({"seed_history": [("reading", "output"), ...], "then": "space"})
```

その確認の後に「history スコアのチューニング」（時間減衰係数・閾値）を先に試みる。
辞書への書き込みは最後の手段。
